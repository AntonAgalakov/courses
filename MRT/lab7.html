1 Цель работы

Получить практические навыки работы с ORM-библиотекой ODB в C++ при взаимодействии с PostgreSQL. Научиться:

  • описывать объектную модель с помощью ODB-прагм (#pragma db ...);
  • выполнять CRUD-операции;
  • строить транзакции с несколькими инвариантами и откатом при нарушении;
  • понимать проблему N+1 запросов и её границы применимости.

Предметная область

Студия ведёт парк техники (камеры, объективы, вспышки, штативы, свет) и штат фотографов. Перед съёмкой фотограф получает комплект техники, после — возвращает в стойку. Приложение следит за тем, чтобы:

  • нельзя было выдать единицу техники, которая уже на съёмке;
  • нельзя было уволить фотографа, у которого на руках техника;
  • нельзя было добавить фотографа с дублирующимся email;
  • нельзя было добавить технику с дублирующимся инвентарным номером.

Что уже реализовано в проекте

  • три ODB-класса: Employee, Asset, Assignment (у Employee прагмы написаны как эталон, у остальных — TODO);
  • графический интерфейс: вкладки «Фотографы» и «Техника», диалоги, таблицы с бейджами, кнопки, обработка горячих клавиш;
  • частично сервисный слой Service — четыре метода-образца, пять методов с TODO;
  • схема БД sql/schema.sql;
  • конфигурация сборки CMake с автоматической генерацией ODB-кода;
  • инструкция по установке PostgreSQL и запуску (README.md).
Важно. Графический интерфейс, схему БД, конфигурацию CMake и файл main.cpp менять не нужно. Все задачи — в трёх файлах: include/domain/asset.hxx, include/domain/assignment.hxx, src/service.cpp. В каждом TODO-блоке описан контракт метода: что он делает, какие ошибки бросает и по каким критериям проверяется.

Часть 4. Добавление техники в каталог TODO
Файл: src/service.cpp, метод Service::addAsset
Вызывается из: диалога «+ Техника» после клика «Сохранить».
Контракт:
  • Вход: inv — инвентарный номер, model, cat — текстовые поля.
  • Успех: в БД появляется одна запись в assets со статусом assigned = false. Ничего не возвращается (void).
  • Ошибка: выбросить DomainError, если такой инвентарный номер уже есть, текст: "Инвентарный номер <inv> уже существует".
  • При ошибке изменения в БД не применяются.
Критерии готовности:
  1. После добавления — строка в таблице с бейджем «В стойке».
  2. Попытка добавить дубль инвентарного номера — в БД остаётся одна запись.
Подсказка: в этом же файле метод addEmployee делает то же самое для сотрудника. Структура решения идентична.
Часть 5. Обновление данных фотографа TODO
Файл: src/service.cpp, метод Service::updateEmployee
Вызывается из: диалога редактирования фотографа после клика «Сохранить».
Контракт:
  • Вход: id — существующий фотограф; name, email — новые значения; active — true (в штате) или false (уволен).
  • Успех: поля в БД обновлены, ничего не возвращается.
  • Ошибки — выбросить DomainError:
    1. если email изменился и такой email уже есть у другого фотографа, текст: "Фотограф с email <email> уже существует";
    2. если active становится false, а за фотографом есть техника на съёмке, текст: "У фотографа на руках техника — сначала примите возврат".
  • При любой из ошибок изменения в БД не применяются.
Критерии готовности:
  1. Изменение ФИО/email/статуса без нарушения правил — сохраняется и видно в таблице.
  2. Попытка сохранить дубль email — диалог не закрывается.
  3. Попытка уволить с техникой на съёмке — статус в таблице не меняется.
Подсказка: «за фотографом числится техника» — это запрос к таблице assignments по employee_id с фильтром «нет даты возврата». У nullable-поля returnedAt_ в ODB есть метод is_null().
Часть 6. Список техники с держателем TODO
Файл: src/service.cpp, метод Service::assets
Вызывается из: при каждой перерисовке вкладки «Техника».
Контракт:
  • Успех: возвращает std::vector<AssetRow>, по одному элементу на каждую единицу техники. В поле holder — ФИО фотографа, если техника на съёмке, или пустая строка, если в стойке.
  • Ошибок не бросает (пустая БД — пустой вектор).
Критерии готовности:
  1. После выдачи техники её holder = ФИО фотографа.
  2. После возврата holder = "".
  3. Фильтр «В стойке» / «На съёмке» в UI работает корректно.
Что такое «N+1 запросов» и почему это упомянуто в части 6.

Представьте, что в базе 100 единиц техники.

  • 1 запрос — получить все 100 единиц из таблицы assets.
  • Для каждой единицы ещё 2 запроса: найти активную выдачу в assignments, найти фотографа в employees.
  • Итого: 1 + 100 × 2 = 201 запрос вместо одного.

Называется «N+1», потому что «1 запрос на список + N запросов на каждую строку списка». Это классическая проблема всех ORM (Hibernate, Entity Framework, SQLAlchemy, ODB) — ORM не «схлопывает» вложенные запросы автоматически.

Что нужно в лабе. Наивное решение с N+1 — достаточно. 100 единиц техники работают мгновенно, код читается за минуту. Но на защите будет вопрос: «Как переписать это на один SQL-запрос с LEFT JOIN?» — нужно уметь объяснить идею, даже если не реализовывать.

Часть 7. Выдача техники фотографу TODO
Файл: src/service.cpp, метод Service::issue
Вызывается из: диалога «Выдать» после клика «Сохранить».
Контракт:
  • Вход: assetId, employeeId — id существующих записей.
  • Успех: техника переходит в статус assigned = true, в assignments появляется запись с issuedAt = текущее время и пустым returnedAt. Ничего не возвращается.
  • Ошибки — выбросить DomainError:
    1. техника уже на съёмке: "Техника уже выдана";
    2. фотограф уволен: "Нельзя выдать уволенному фотографу".
  • При любой ошибке изменения в БД не применяются.
Критерии готовности:
  1. После выдачи: бейдж «На съёмке», «У кого» = ФИО, запись в assignments.
  2. Попытка выдать уже выданную технику — в БД ничего не меняется.
  3. Попытка выдать уволенному — в БД ничего не меняется.
Примитивы ODB: db_.load<T>(id), db_.update(obj), db_.persist(obj), t.commit(). Паттерн транзакции — см. addEmployee.
Часть 8. Возврат техники со съёмки TODO
Файл: src/service.cpp, метод Service::giveBack
Вызывается из: главного окна кнопкой «Принять».
Контракт:
  • Вход: assetId — id техники.
  • Успех: у активной выдачи проставляется returnedAt = текущее время, у техники assigned = false. Ничего не возвращается.
  • Ошибка: выбросить DomainError, если активной выдачи нет (техника уже в стойке), текст: "Нет активной выдачи для этой техники".
  • При ошибке изменения в БД не применяются.
Критерии готовности:
  1. После возврата: бейдж «В стойке», «У кого» = «—», в assignments у записи появилась дата возврата.
  2. Попытка вернуть технику из стойки — в БД ничего не меняется.
  3. Возвращённую технику можно снова выдать другому фотографу.

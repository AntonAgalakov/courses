1. Введение

Git — это программа для контроля версий (version control). Она устанавливается на компьютер и работает поверх обычной файловой системы. Git не заменяет редактор, не запускает код и не «делает магию» — он ведёт учёт изменений в файлах и позволяет возвращаться к любому сохранённому состоянию.

Если сказать ещё точнее: Git хранит снимки состояния проекта и связи между ними. Каждый снимок называется коммитом (commit). Из коммитов складывается история проекта. Git умеет показать, чем один снимок отличается от другого, кто и когда его сделал, и на каком снимке находится проект сейчас.

Дальше в этой главе мы разберём: зачем это нужно, чем Git отличается от других подобных систем, из каких частей он состоит и что происходит с файлом, когда мы его «сохраняем» в историю. В конце — научимся работать в терминале и пройдём первый сквозной пример. Установка Git описана отдельно — в инструкции для Windows и инструкции для Linux.

2. Какую проблему решает контроль версий

Пока проект состоит из одного файла и пишется за один вечер, контроль версий не нужен. Проблемы начинаются, когда:

  • файлов становится много и они связаны между собой;
  • проект живёт недели, месяцы и годы;
  • над проектом работают несколько человек;
  • нужно срочно исправить ошибку в старой версии, не ломая новую;
  • нужно понять, когда и кем была внесена конкретная строка.

Что происходит без системы контроля версий

Типичная картина: папка с файлами вида report.docx, report_v2.docx, report_final.docx, report_final_испр.docx, report_final_испр_2.docx. Никто уже не помнит, чем именно отличаются копии, какая из них актуальна и почему. Если два человека правили одну и ту же копию — правки одного потеряны. Если нужно откатить одну конкретную правку — придётся вручную сравнивать файлы.

Система контроля версий решает эти проблемы системно:

ПроблемаЧто даёт Git
Непонятно, что и когда изменилосьКаждое изменение оформлено коммитом с автором, датой и сообщением. Есть команда git log.
Нужно вернуться к прошлой версииЛюбой коммит можно восстановить полностью или частично.
Несколько человек правят одно и то жеИзменения сливаются (git merge), конфликты видны явно и разрешаются осознанно.

Нужно знать, кто внёс конкретную строкуgit blame показывает автора и коммит для каждой строки файла.

3. Три поколения систем контроля версий

Контроль версий развивался в три этапа. Понимание разницы помогает увидеть, почему Git устроен именно так.

Локальные системы

Простейший вариант: история хранится в той же папке, что и файлы (например, в скрытой подпапке). Работает только на одном компьютере. Если компьютер сломается — история пропадёт вместе с файлами. Пример: RCS.

Централизованные системы

Есть один общий сервер, на котором лежит вся история. Каждый разработчик подключается к серверу и берёт оттуда файлы. Плюс — история в одном месте, все видят одно и то же. Минус — без сети работать нельзя, а падение сервера останавливает всю команду. Примеры: SVN, CVS.

Распределённые системы (Git)

У каждого разработчика есть полная копия истории, а не только последние файлы. Сервер (например, GitHub) — это просто один из узлов, с которым удобно синхронизироваться. Следствия:

  • почти все операции (коммит, просмотр истории, переключение веток) выполняются локально и мгновенно;
  • можно работать без интернета;
  • если сервер упадёт — история сохранится у каждого участника;
  • любой клон репозитория — это полноценная резервная копия.
Важно понять

Git — распределённая система. Это не «облако, в котором лежит код». Это локальная программа, которая умеет синхронизироваться с другими копиями той же истории.

4. Что такое Git

Git — распределённая система контроля версий, созданная Линусом Торвальдсом в 2005 году для разработки ядра Linux. Сегодня это стандарт де-факто в разработке ПО.

Три ключевых свойства Git, которые важно понимать с самого начала:

4.1. Git хранит снимки, а не разницы

Многие системы контроля версий хранят изменения: «в файле A добавили строку, в файле B удалили строку». Git устроен иначе: каждый коммит — это снимок всего проекта целиком на момент коммита. Если файл не менялся с прошлого коммита, Git не хранит его заново — он ссылается на ту же самую копию. Поэтому снимки не раздувают репозиторий.

4.2. Почти всё делается локально

Вся история лежит в скрытой папке .git/ внутри проекта. Коммит, просмотр логов, переключение веток, сравнение версий — всё это работает без интернета. Сеть нужна только для обмена с другими копиями (git push, git pull).

4.3. Целостность через хеши

Каждый объект в Git (файл, папка, коммит) идентифицируется криптографическим хешем — длинной строкой из 40 шестнадцатеричных символов. Обычно используют сокращение до 7 символов. Пример хеша коммита: 3f2a1b7. Если содержимое объекта изменить хотя бы на байт — хеш станет другим. Это гарантирует, что история не «тихо испортится»: любое искажение сразу обнаружится.

Что нужно запомнить

Git — это локальная программа. Вся история проекта хранится в папке .git/. Каждый коммит — снимок всего проекта, адресуемый по хешу.

Рис. 1. Три области Git и команды перехода между ними

5.1. Working Directory — рабочая папка

Это обычная папка на диске, в которой лежат файлы проекта. Вы открываете их в редакторе и меняете напрямую. Пока изменения не добавлены в индекс, Git их «не видит» в смысле коммита: он знает, что файл отличается от последнего снимка, но сохранять его в историю не будет, пока Вы явно не скажете.

5.2. Staging Area (индекс) — область подготовки

Это промежуточный слой между рабочей папкой и историей. Сюда попадают файлы, которые должны войти в следующий коммит. Зачем он нужен:

  • можно изменить десять файлов, а закоммитить только три;
  • можно разбить одну большую правку на несколько логичных коммитов;
  • перед коммитом можно посмотреть, что именно попадёт в историю (git diff --staged).

Файл попадает в индекс командой git add. Убрать его из индекса (не трогая содержимое) — командой git restore --staged <файл>.

5.3. Repository — хранилище истории

Это папка .git/ в корне проекта. В ней лежат все коммиты, все версии всех файлов и служебные данные. Файлы попадают сюда командой git commit — в виде нового снимка. Напрямую в .git/ ничего не трогают: вся работа идёт через команды Git.

Не трогайте .git/ руками

Внутри .git/ лежит вся история проекта. Удаление или случайное изменение файлов внутри этой папки может привести к потере данных. Работайте с Git только через команды.

6. Жизненный цикл файла

У файла в Git есть четыре основных состояния. Понимание переходов между ними снимает 90% путаницы.

Untracked git add→ Staged git commit→ Committed (unmodified)
Modified git add→ Staged
↑ правка файла в редакторе переводит Committed в Modified

7. Что такое коммит

Коммит — это зафиксированный снимок проекта. Технически коммит — это объект, который содержит:

  • ссылку на снимок файлов (дерево каталогов и файлов на этот момент);
  • автора и дату создания;
  • сообщение — короткое описание, что изменилось;
  • ссылку на родительский коммит (или на несколько, если это слияние);
  • собственный хеш — уникальный идентификатор.

Упрощённо коммит выглядит так:

# псевдо-структура коммита
commit 3f2a1b7...
Author: Иван <ivan@example.com>
Date:   Mon Oct 20 14:32:11 2026 +0300

    Добавить приветствие в hello.txt

    tree      a1b2c3d...    # снимок всех файлов проекта
    parent    —             # у первого коммита родителя нет

Зачем нужно сообщение коммита

Сообщение — это единственное, что объяснит через полгода (Вам же самому) зачем было сделано изменение. Хорошая практика:

  • первая строка — до 50 символов, в повелительном наклонении: «Добавить форму входа», «Исправить опечатку в README»;
  • если нужно — пустая строка и подробное описание ниже;
  • не «фиксы», не «ещё немного поправил», не «asdf».

Коммит — это не сохранение файла

Важно не путать: Ctrl+S в редакторе сохраняет файл на диск, но не создаёт коммит. Коммит создаётся только командой git commit и фиксирует состояние всех файлов, которые были в индексе на этот момент.

8. Как устроена история

Коммиты связаны друг с другом ссылками на родителей. Это образует направленный граф: у каждого коммита (кроме первого) ровно один родитель, у коммита-слияния — два или больше. У первого коммита в репозитории родителя нет, его называют root commit.

a1b2c3droot ← e4f5a6b2-й ← 7c8d9e03-й ← 3f2a1b7последнийmain · HEAD

Рис. 3. Цепочка коммитов. Стрелки означают «родитель»: у коммита 3f2a1b7 родитель — 7c8d9e0, и так далее до root.

Слово main на схеме — это ветка, то есть именованная ссылка на конкретный коммит. Слово HEAD — указатель на текущий коммит (о нём ниже). По умолчанию новая ветка называется main (в старых версиях Git — master).

Почему стрелки назад

Каждый коммит знает своего родителя, а не наоборот. Из последнего коммита можно пройти всю историю назад до самого первого. Поэтому git log показывает историю начиная с текущего коммита — и идёт в прошлое.

9. HEAD и ветки (кратко)

Полностью ветки и HEAD разбираются в главе 4, но одно понятие нужно уже сейчас.

HEAD — это специальный указатель, который говорит Git: «вот коммит, на котором Вы сейчас находитесь». Когда Вы делаете новый коммит, HEAD (и ветка, на которую он указывает) переезжает на только что созданный коммит. В обычном состоянии HEAD указывает на ветку, а ветка — на коммит.

Проверить, где сейчас HEAD, можно командой:

$ git status
On branch main
...

Строка On branch main означает: HEAD указывает на ветку main, а она — на последний коммит этой ветки.

10. Терминал: MSYS2 UCRT64 и Linux

Вся практика в этой главе (и во всём учебнике) выполняется в терминале. Если Вы ещё не установили инструменты — вернитесь к инструкции для Windows или для Linux.

На Windows используется не cmd и не PowerShell, а MSYS2 UCRT64 — окружение, которое даёт Linux-подобный терминал и все инструменты для C (GCC, Make, CUnit, Git). На Linux подойдёт любой стандартный терминал.

Почему UCRT64, а не Git Bash

Git Bash умеет только команды Git. UCRT64 — это полноценная среда: в ней одновременно доступны git, gcc, make и CUnit. В контрольной работе понадобятся все четыре, поэтому выбран именно UCRT64.

10.1. Как открыть UCRT64 (Windows)

  1. Нажмите «Пуск» → найдите MSYS2 UCRT64 → запустите.
  2. Откроется окно с приглашением вида: 
    user@machine UCRT64 ~
$
    Здесь ~ — Ваша домашняя папка (обычно C:\Users\<имя>).
  3. Если при установке MSYS2 было добавлено контекстное меню — можно в Проводнике открыть нужную папку, кликнуть правой кнопкой и выбрать MSYS2 UCRT64 Here.

10.2. Главное отличие: пути в стиле Unix

Внутри UCRT64 диск C: превращается в /c/. Это самая частая точка путаницы у новичков. Примеры:

Windows-путьПуть в UCRT64
C:\Users\ivan/c/Users/ivan или ~
C:\Projects\hello-git/c/Projects/hello-git
D:\Work\test/d/Work/test

Обратные слэши (\) в UCRT64 как разделители пути не работают — используйте прямые (/), как в Linux.

10.3. Как перейти в папку проекта

Например, проект находится в C:\Projects\hello-git: 

$ cd /c/Projects/hello-git
$ pwd
/c/Projects/hello-git

Если проект в домашней папке — короче: cd ~/hello-git. Команда pwd всегда покажет, где Вы сейчас.

10.4. Проверка, что всё на месте

В UCRT64 выполните три команды:

$ git --version
$ gcc --version
$ make --version

Каждая должна вывести версию. Если какая-то не найдена — вернитесь к инструкции по установке Windows и проверьте, что установлен нужный пакет.

Перед первым коммитом

Git должен знать Ваши имя и email — иначе git commit откажется работать. Если ещё не настраивали — загляните в главу 2 или выполните прямо сейчас: 

$ git config --global user.name "Ваше Имя"
$ git config --global user.email "you@example.com"

10.5. Linux и macOS

На Linux откройте любой терминал (GNOME Terminal, Konsole, XTerm — без разницы; часто Ctrl+Alt+T). На macOS — Terminal.app или iTerm2. Пути обычные: /home/user/projects, ~/projects. Все команды ниже работают так же, как в UCRT64.

Что не работает в UCRT64

Команды Windows-консоли вроде dir, copy, type, cls — не работают. Используйте их аналоги из Linux: ls, cp, cat, clear. Git-команды при этом работают везде одинаково.

11. Базовые команды терминала

Здесь перечислены все команды терминала, которые встретятся в практическом примере. Их немного, и они очень простые. Git-команды разберём отдельно — в сквозном примере.

Что такое «текущая папка»

Терминал всегда «находится» в какой-то папке. Если Вы пишете mkdir hello, папка hello создастся именно в текущей папке. Если Вы пишете git status, Git будет искать репозиторий начиная с текущей папки. Чтобы не путаться, перед началом работы полезно выполнить pwd — увидеть, где Вы.

11.2. Как читать примеры в учебнике

В примерах команд строка $ в начале — это приглашение командной строки. Её не нужно вводить. Вводится только то, что идёт после неё. Строки без $ и с серым цветом — это вывод Git, его набирать не надо. 

$ git --version        # ← это вводите Вы (без $)
git version 2.55.0   # ← это выводит Git

В некоторых местах в примерах будут встречаться комментарии (серым курсивом после #) — это пояснения, их тоже набирать не нужно.

Совет

Все команды из примеров можно копировать прямо из учебника и вставлять в терминал. Это нормально и не считается читерством — на первых порах так делают все.

11.3. Почему не графический интерфейс

Графические клиенты скрывают, что именно происходит. Пока Вы не увидели своими глазами вывод git status и git log, Вы не понимаете, как устроен Git. После — можете пользоваться чем угодно, включая GUI. Но сначала — терминал.

12. Сквозной пример: от пустой папки до первого коммита

Пройдём весь путь по шагам. Все команды выполняются в терминале (на Windows — в MSYS2 UCRT64, на Linux — в любом терминале). Вывод команд показан как есть. После каждого шага разобрано, что означает каждая команда и каждая строка вывода.

Шаг 1. Создать папку проекта и инициализировать репозиторий

Создаём новую папку hello-git и превращаем её в Git-репозиторий.

$ mkdir hello-git
$ cd hello-git
$ git init
Initialized empty Git repository in /home/user/hello-git/.git/
Разбор команд
  • mkdir hello-git — команда mkdir (make directory) создаёт новую папку. hello-git — имя папки. В текущей папке появится подпапка hello-git.
  • cd hello-git — команда cd (change directory) переходит в указанную папку. После выполнения Вы окажетесь внутри hello-git, и все следующие команды будут выполняться уже в ней.
  • git init — git вызывает программу Git, init (initialize) создаёт новый пустой репозиторий в текущей папке. Внутри hello-git появится скрытая папка .git/, в которой будет храниться вся история проекта.
Разбор вывода
Что вывел Git
Initialized empty Git repository in /home/user/hello-git/.git/
«Инициализирован пустой Git-репозиторий в /home/user/hello-git/.git/». Git сообщает, что репозиторий создан, и показывает полный путь к новой папке .git/. В UCRT64 путь будет выглядеть как /c/Users/<имя>/hello-git/.git/ — это одна и та же папка, записанная по-разному.

Состояние: репозиторий существует, но в нём пока ни одного коммита. Файлов в проекте нет.

Шаг 2. Создать файл

Создаём файл hello.txt с одной строкой текста и смотрим, как Git его видит.

$ echo "Привет, Git!" > hello.txt
$ git status
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	hello.txt

nothing added to commit but untracked files present (use "git add" to track)
Разбор команд
  • echo "Привет, Git!" — команда echo выводит текст на экран. Сама по себе она просто напечатала бы «Привет, Git!» в терминале.
  • > — символ перенаправления. Он берёт то, что должно было вывестись на экран, и записывает в файл. Если файла нет — он создаётся. Если файл уже есть — он будет перезаписан.
  • hello.txt — имя файла, в который пишем.
  • Итого: echo "Привет, Git!" > hello.txt создаёт файл hello.txt с текстом «Привет, Git!».
  • git status — команда status показывает текущее состояние репозитория: какие файлы изменены, какие добавлены в индекс, на какой ветке Вы находитесь. Это самая часто используемая команда Git — ей стоит пользоваться перед каждым add и commit.
Разбор вывода
Что вывел Git
On branch main
«На ветке main». Git сообщает, что Вы находитесь на ветке main — это главная ветка, созданная по умолчанию при git init.
No commits yet
«Коммитов пока нет». В репозитории ещё не сделано ни одного коммита.
Untracked files:
«Неотслеживаемые файлы». Раздел, в котором перечислены файлы, существующие в рабочей папке, но не входящие ни в один коммит. Git их видит, но ещё не «взял под контроль».
(use "git add <file>..." to include in what will be committed)
Подсказка от Git: «используйте git add <файл>..., чтобы включить файл в следующий коммит».
hello.txt
Собственно имя неотслеживаемого файла. Отступ слева означает, что файл относится к разделу «Untracked files».
nothing added to commit but untracked files present (use "git add" to track)
«Ничего не добавлено к коммиту, но есть неотслеживаемые файлы (используйте git add, чтобы начать их отслеживать)». Итоговая фраза: делать коммит пока не с чем, потому что в индексе пусто.

Состояние файла: Untracked. Git видит, что файл появился, но не хранит его в истории.

Шаг 3. Добавить файл в индекс

Переводим файл из рабочей папки в staging area — подготовку к коммиту.

$ git add hello.txt
$ git status
On branch main

No commits yet

Changes to be committed:
  (use "git rm --cached <file>..." to unstage)
	new file:   hello.txt
Разбор команд
  • git add hello.txt — команда git add добавляет указанный файл в индекс (staging area). Файл ещё не попал в историю, но уже «подготовлен» к следующему коммиту. Содержимое файла при этом не меняется.
  • hello.txt — имя файла, который добавляем. Можно было указать git add . (точка = «все файлы в текущей папке и подпапках»), но для наглядности указываем файл явно.
  • git status — снова смотрим состояние, чтобы увидеть, что изменилось.
Разбор вывода
Что вывел Git
On branch main
Всё та же ветка main.
No commits yet
Коммитов по-прежнему нет.
Changes to be committed:
«Изменения, которые будут закоммичены». Раздел, в котором перечислены файлы из индекса — то есть то, что попадёт в следующий коммит.
(use "git rm --cached <file>..." to unstage)
Подсказка: «используйте git rm --cached <файл>..., чтобы убрать файл из индекса». (На практике чаще используют git restore --staged <файл> — об этом в главе 3.)
new file: hello.txt
«Новый файл: hello.txt». Ключевое слово new file означает, что файл добавляется в историю впервые. Дальше отступ, имя файла. Файл теперь в индексе.

Состояние файла: Staged. Файл подготовлен и попадёт в следующий коммит.

Шаг 4. Сделать первый коммит

Сохраняем снимок проекта в историю. Файл из индекса переходит в репозиторий.

$ git commit -m "Добавить приветствие в hello.txt"
[main (root-commit) 3f2a1b7] Добавить приветствие в hello.txt
 1 file changed, 1 insertion(+)
 create mode 100644 hello.txt
Разбор команды
  • git commit — создаёт новый коммит из того, что сейчас лежит в индексе. Всё, что было добавлено через git add, попадёт в снимок.
  • -m — флаг (ключ) «message». Позволяет передать сообщение коммита прямо в командной строке, не открывая редактор.
  • "Добавить приветствие в hello.txt" — само сообщение коммита, в кавычках. Это текст, который останется в истории и объяснит будущему читателю, что было сделано.
Разбор вывода
Что вывел Git
[main (root-commit) 3f2a1b7] Добавить приветствие в hello.txt
Первая строка: main — ветка, в которую добавлен коммит; root-commit — это самый первый коммит в репозитории (у него нет родителя); 3f2a1b7 — сокращённый хеш нового коммита (у Вас он будет другим); далее в квадратных скобках — сообщение коммита.
1 file changed, 1 insertion(+)
«1 файл изменён, 1 вставка (+)». Git подводит статистику: в коммите участвует один файл, в нём появилась одна новая строка. Знак + означает добавление (было бы - — удаление).
create mode 100644 hello.txt
«Создан файл hello.txt с режимом доступа 100644». Число 100644 — это стандартные права обычного файла в Git (не исполняемого, не символической ссылки). Для нас это просто служебная информация о том, что файл создан.

Состояние файла: Committed. В истории появился первый коммит 3f2a1b7. root-commit означает, что это самый первый коммит в репозитории.

Шаг 5. Изменить файл

Дописываем в файл вторую строку. Файл уже в истории, но теперь отличается от последнего снимка.

$ echo "Вторая строка" >> hello.txt
$ git status
On branch main
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   hello.txt

no changes added to commit (use "git add" and/or "git commit -a")
Разбор команд
  • echo "Вторая строка" — выводит текст «Вторая строка».
  • >> — двойное перенаправление. В отличие от одиночного >, оно не перезаписывает файл, а дописывает в конец. Именно поэтому первая строка файла остаётся на месте.
  • hello.txt — файл, в конец которого дописываем строку.
  • git status — снова смотрим состояние.
Разбор вывода
Что вывел Git
On branch main
Всё та же ветка main.
Changes not staged for commit:
«Изменения, не подготовленные к коммиту». Раздел, в котором перечислены файлы, отличающиеся от последнего коммита, но пока не добавленные в индекс. Здесь уже нет строки «No commits yet», потому что коммит в репозитории появился на предыдущем шаге.
(use "git add <file>..." to update what will be committed)
Подсказка: «используйте git add, чтобы обновить то, что попадёт в коммит».
(use "git restore <file>..." to discard changes in working directory)
Подсказка: «используйте git restore <файл>..., чтобы отменить изменения в рабочей папке». ⚠️ Это действие уничтожит правки в файле, будьте осторожны.
modified: hello.txt
«Изменён: hello.txt». Ключевое слово modified говорит, что файл уже отслеживается Git (был в прошлом коммите), но его содержимое в рабочей папке отличается от того, что в истории.
no changes added to commit (use "git add" and/or "git commit -a")
«Нет изменений, добавленных к коммиту (используйте git add и/или git commit -a)». Итог: в индексе пусто, коммитить пока нечего.

Состояние файла: Modified. Git видит, что файл отличается от последнего коммита, но в индекс изменение не добавлено.

Шаг 6. Снова добавить в индекс и закоммитить

Повторяем стандартный цикл: add → commit.

$ git add hello.txt
$ git commit -m "Добавить вторую строку в hello.txt"
[main 9d1e4c2] Добавить вторую строку в hello.txt
 1 file changed, 1 insertion(+)
Разбор команд
  • git add hello.txt — снова добавляет файл в индекс. Теперь в индексе актуальная версия файла (с двумя строками).
  • git commit -m "..." — создаёт новый коммит. Смысл тот же, что на шаге 4, только это уже второй коммит в истории, а не root.
Разбор вывода
Что вывел Git
[main 9d1e4c2] Добавить вторую строку в hello.txt
Коммит добавлен в ветку main, его сокращённый хеш — 9d1e4c2 (у Вас будет другой). Слова root-commit здесь уже нет — это обычный коммит с родителем.
1 file changed, 1 insertion(+)
«1 файл изменён, 1 вставка». В коммите участвует один файл, добавлена одна строка. Строка create mode ... не появляется, потому что файл уже существует в истории — он не создаётся заново, а изменяется.

Состояние: в истории уже два коммита: 3f2a1b7 → 9d1e4c2. Ветка main и HEAD теперь указывают на 9d1e4c2.

Шаг 7. Посмотреть историю

Проверяем, что оба коммита на месте.

$ git log --oneline
9d1e4c2 (HEAD -> main) Добавить вторую строку в hello.txt
3f2a1b7 Добавить приветствие в hello.txt
Разбор команды
  • git log — показывает историю коммитов. По умолчанию выводит каждый коммит с полной информацией (автор, дата, хеш, сообщение) — это занимает много места.
  • --oneline — флаг «одной строкой». Ужимает каждый коммит до одной строки: сокращённый хеш + сообщение. Самый удобный формат для повседневной работы.
Разбор вывода
Что вывел Git (сверху — самые новые коммиты)
9d1e4c2 (HEAD -> main) Добавить вторую строку в hello.txt
Первая строка — самый последний (второй) коммит. 9d1e4c2 — его сокращённый хеш. HEAD -> main — служебная пометка: HEAD указывает на ветку main, а она — на этот коммит. Далее — сообщение коммита.
3f2a1b7 Добавить приветствие в hello.txt
Вторая строка — первый (root) коммит. Пометки HEAD здесь нет, потому что HEAD на него не указывает — он на самом последнем коммите.

Что мы видим: две строки — два коммита, от нового к старому. HEAD -> main показывает, что HEAD указывает на ветку main, а она — на коммит 9d1e4c2.

Итог примера

Мы прошли все четыре состояния файла: Untracked → Staged → Committed → Modified → Staged → Committed. И получили историю из двух коммитов. Это и есть базовый рабочий цикл Git, который будет повторяться постоянно.

13. Git и GitHub — не одно и то же

Это самое частое смешение понятий у новичков.

GitGitHub
Что этоПрограмма для контроля версийВеб-сервис для хранения Git-репозиториев
Где работаетЛокально на Вашем компьютереВ интернете, на серверах компании
Нужен интернет?Нет (кроме синхронизации)Да
Кто сделалЛинус Торвальдс, 2005Компания GitHub, 2008 (с 2018 — у Microsoft)
Аналоги—GitLab, Bitbucket, Gitea

Грубо говоря: Git — это инструмент, GitHub — это площадка, где этим инструментом удобно пользоваться совместно. Можно пользоваться Git вообще без GitHub — и это нормально. А GitHub без Git не имеет смысла.

14. Частые заблуждения

«Git сохраняет файлы автоматически»

Нет. Git создаёт снимок только по команде git commit. Сохранение файла в редакторе — это просто запись на диск, история проекта от этого не меняется.

«Коммит — это сохранение одного файла»

Нет. Коммит — это снимок всего проекта на момент коммита. Просто в индекс перед коммитом попадают только те файлы, которые Вы туда добавили. Остальные файлы в снимок войдут в том виде, в каком были в предыдущем коммите.

«Git хранит все версии файлов целиком, поэтому репозиторий огромный»

Не совсем. Git действительно мыслит снимками, но физически одинаковые файлы хранятся один раз. Если в коммите файл не менялся, новый коммит просто ссылается на тот же объект. Поэтому даже долгая история занимает немного места.

«Без GitHub Git не работает»

Работает. GitHub — лишь один из способов поделиться репозиторием. Git полностью функционален локально.

«Ветка — это копия папки с файлами»

Нет. Ветка в Git — это всего лишь указатель на коммит (файл с 40-символьным хешем внутри). Создание ветки не копирует файлы и не занимает места. Подробно — в главе 4.

«Если удалить файл, он удалится из истории»

Нет. Удаление файла в рабочей папке (и коммит этого удаления) означает «в этом снимке файла нет». Но во всех предыдущих коммитах он остаётся. История неизменна — это одно из главных свойств Git.

15. Итоги главы

Что нужно вынести из главы 1:

  • Git — распределённая система контроля версий, работающая локально.
  • Git хранит снимки проекта (коммиты), связанные ссылками на родителей.
  • Каждый объект в Git идентифицируется хешем; история неизменна.
  • У Git три области: рабочая папка → индекс (staging) → репозиторий.
  • Файл проходит состояния: Untracked → Staged → Committed → Modified и обратно.
  • Базовый цикл: git add → git commit → (правки) → git add → git commit.
  • HEAD — указатель на текущий коммит (обычно через ветку, например main).
  • Git ≠ GitHub: Git — программа, GitHub — сервис.
  • Установка инструментов — отдельная инструкция: Windows / Linux.
  • Вся практика в учебнике — в терминале; на Windows это MSYS2 UCRT64, на Linux — любой терминал.
  • В UCRT64 пути записываются в стиле Unix: C:\Users\ivan → /c/Users/ivan.
  • Из базовых команд терминала достаточно знать: pwd, ls, cd, mkdir, echo, >, >>, cat.

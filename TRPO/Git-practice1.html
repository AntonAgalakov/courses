1. Что мы сделаем

Сценарий: Вы пишете небольшую программу на C, постепенно наращиваете её функциональность и коммитите после каждого шага. Затем намеренно вносите ошибку, замечаете её, смотрите историю, перемещаетесь на предыдущий коммит, убеждаетесь, что там всё работало, возвращаетесь на последний и исправляете ошибку новым коммитом.

a1b2c3d Hello World → e4f5a6b + функция sum → 7c8d9e0 + цикл → 3f2a1b7 баг! bad → 9d1e4c2 исправление main

Рис. 1. Пять коммитов, которые мы создадим. Все хеши на схеме — примеры. У Вас они будут другими.

Главный навык — не бояться перемещаться по истории. В Git можно в любой момент «отмотать» рабочую папку к любому коммиту, посмотреть, как всё было, скомпилировать и запустить — и так же легко вернуться обратно. Ничего не ломается, пока Вы не пытаетесь делать в этом состоянии новые коммиты, не создав ветку.

2. Хеши у Вас будут другими

Прочтите до того, как начнёте

В этой практике Вы увидите много строк вида 7c8d9e0, 3f2a1b7 и т.п. Это хеши коммитов — уникальные идентификаторы, которые Git вычисляет для каждого коммита. У Вас они будут другими. Все хеши в этом документе — примеры для иллюстрации. Свои хеши Вы найдёте в git log --oneline.

2.1. Что такое хеш коммита

Хеш — это 40-символьная строка из цифр и букв a–f. Git вычисляет её из содержимого коммита: файлов, автора, даты, сообщения и родительского коммита. Любое изменение хотя бы одного байта даёт другой хеш. Поэтому у двух людей, делающих «одинаковые» коммиты в разное время, хеши всё равно будут разные — например, из-за разницы в дате и времени.

Обычно хеш записывают сокращённо — первые 7 символов. В git log --oneline Git показывает именно такую короткую форму: 

$ git log --oneline
3f2a1b7 (HEAD -> main) Оптимизировать sum
7c8d9e0 Добавить цикл вывода чисел
e4f5a6b Добавить функцию sum и вывод её результата
a1b2c3d Добавить Hello World на C

2.2. Почему их нельзя копировать из учебника

Если Вы скопируете команду git switch --detach 7c8d9e0 из примера и вставите в свой терминал, Git ответит примерно так: 

$ git switch --detach 7c8d9e0
fatal: bad revision '7c8d9e0'

Это нормально: в Вашем репозитории нет коммита с таким хешем, потому что Ваш коммит «Добавить цикл вывода чисел» имеет другой хеш. Нужно подставить свой — тот, который Вы видите в git log.

2.3. Как найти свой хеш

Есть три способа найти нужный хеш:

  1. Посмотреть в git log --oneline. Самое простое: выполнить команду, найти нужную строку по сообщению коммита и взять первые 7 символов.
  2. Найти по сообщению: git log --oneline --grep="цикл" выведет только коммиты, в сообщении которых встречается «цикл». Удобно, когда история длинная.
  3. Посмотреть последний коммит: git log --oneline -1 выведет только самый свежий.
Правило на всю практику

Везде, где в команде стоит хеш — подставляйте свой. Хеши из примеров (a1b2c3d, 7c8d9e0, 3f2a1b7, 9d1e4c2) — только для иллюстрации. Свои хеши Вы выпишете в разделе 9 и будете использовать дальше. Если ошиблись — Git скажет fatal: bad revision, и Вы просто попробуете ещё раз. Ничего не сломается.

3. Подготовка: компилятор и Git

Нам понадобятся две вещи: установленный Git (глава 1) и компилятор C — программа, которая превращает исходный код в исполняемый файл. Самый распространённый — gcc. 

$ git --version

$ gcc --version
gcc (Ubuntu 13.2.0-23ubuntu4) 13.2.0
Разбор вывода

gcc (Ubuntu 13.2.0...) 13.2.0
Компилятор установлен. У Вас будет другая версия и платформа — это нормально.

4. Создание проекта

Шаг 1. Создать папку и инициализировать репозиторий

Пустая папка превращается в Git-репозиторий с веткой main.

$ mkdir c-git-practice
$ cd c-git-practice
$ git init
Initialized empty Git repository in /home/user/c-git-practice/.git/
Разбор команд
  • mkdir c-git-practice — создаёт папку проекта.
  • cd c-git-practice — переходим в неё.
  • git init — создаёт в папке скрытый подкаталог .git/ — там будет вся история.

Состояние: репозиторий существует, ни одного коммита, ни одного файла.

Шаг 2. Создать .gitignore для C

Исключаем из Git исполняемые и объектные файлы — они генерируются компилятором и не должны попадать в историю.

$ echo "prog" > .gitignore
$ echo "a.out" >> .gitignore
$ echo "*.o" >> .gitignore
$ cat .gitignore
prog
a.out
*.o
Разбор команд
  • echo "prog" > .gitignore — создаёт .gitignore с первой строкой prog. Мы будем компилировать в файл prog, его Git должен игнорировать.
  • >> — дописывает в конец файла. Так появляются a.out (имя по умолчанию у gcc) и *.o (объектные файлы).
  • cat .gitignore — показывает содержимое.

Состояние: в папке один файл .gitignore, untracked.

5. Коммит 1: Hello, World

Шаг 3. Написать программу

Минимальный C-код: выводит одну строку и завершается.

Откройте файл prog.c в любом редакторе (VS Code, Notepad, nano — не важно) и напишите: 

#include <stdio.h>

int main(void) {
    printf("Hello, World!\n");
    return 0;
}
Разбор кода
  • #include <stdio.h> — подключает стандартную библиотеку ввода-вывода. Без неё не будет printf.
  • int main(void) — точка входа. Возвращает целое (0 = успех).
  • printf(...) — печатает строку. \n — перевод строки.
  • return 0; — сообщает ОС, что программа завершилась успешно.
$ git status
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	.gitignore
	prog.c

nothing added to commit but untracked files present (use "git add" to track)

Состояние: два untracked-файла, индекс пуст, коммитов нет.

Шаг 4. Первый коммит

Добавляем оба файла в индекс и коммитим.

$ git add .gitignore prog.c
$ git commit -m "Добавить Hello World на C"
[main (root-commit) a1b2c3d] Добавить Hello World на C
 2 files changed, 8 insertions(+)
 create mode 100644 .gitignore
 create mode 100644 prog.c
Ваш хеш будет другим

В строке [main (root-commit) a1b2c3d] число a1b2c3d — это пример. У Вас Git выведет свой хеш, например b7e4f21. Запомните его — это первый коммит, его мы будем сравнивать позже. Впрочем, если забудете, всегда можно посмотреть через git log.

Состояние: первый коммит создан. Хеш у Вас свой — запишите его.

Шаг 5. Скомпилировать и запустить

Убеждаемся, что программа работает и скомпилированный файл Git игнорирует.

$ gcc prog.c -o prog
$ ./prog
Hello, World!

$ git status
On branch main
nothing to commit, working tree clean

Состояние: программа работает, файл prog создан, но Git его игнорирует — рабочая папка clean.

6. Коммит 2: функция сложения

Шаг 6. Дописать функцию

Добавляем функцию sum(a, b) и печатаем результат.

#include <stdio.h>

int sum(int a, int b) {
    return a + b;
}

int main(void) {
    printf("Hello, World!\n");
    printf("2 + 3 = %d\n", sum(2, 3));
    return 0;
}
Разбор кода
  • int sum(int a, int b) — функция, возвращает сумму.
  • return a + b; — тело функции. Пока она правильная — запомните эту строку.
  • printf("2 + 3 = %d\n", sum(2, 3)); — печатает строку, подставляя в %d результат sum(2, 3). Ожидаем увидеть 2 + 3 = 5.

Смотрим diff:

$ git diff
diff --git a/prog.c b/prog.c
@@ -1,6 +1,11 @@
 #include <stdio.h>
 
+int sum(int a, int b) {
+    return a + b;
+}
+
 int main(void) {
     printf("Hello, World!\n");
+    printf("2 + 3 = %d\n", sum(2, 3));
     return 0;
 }

Состояние: prog.c изменён, но не в индексе.

Шаг 7. Скомпилировать, запустить, закоммитить

$ gcc prog.c -o prog
$ ./prog
Hello, World!
2 + 3 = 5

$ git add prog.c
$ git commit -m "Добавить функцию sum и вывод её результата"
[main e4f5a6b] Добавить функцию sum и вывод её результата
 1 file changed, 5 insertions(+)
Снова: хеш у Вас другой

e4f5a6b — пример. У Вас Git выведет свой. Не пытайтесь использовать e4f5a6b в командах — он не найдётся в Вашем репозитории.

Состояние: два коммита. Хеш второго запишите — он понадобится для сравнений.

7. Коммит 3: цикл вывода чисел

Шаг 8. Добавить цикл

Новая функция print_numbers(n) печатает числа от 1 до n.

#include <stdio.h>

int sum(int a, int b) {
    return a + b;
}

void print_numbers(int n) {
    for (int i = 1; i <= n; i++) {
        printf("%d ", i);
    }
    printf("\n");
}

int main(void) {
    printf("Hello, World!\n");
    printf("2 + 3 = %d\n", sum(2, 3));
    printf("Числа от 1 до 5: ");
    print_numbers(5);
    return 0;
}
Разбор кода
  • void print_numbers(int n) — ничего не возвращает (void), принимает одно число.
  • for (int i = 1; i <= n; i++) — цикл: i от 1 до n включительно.
  • printf("%d ", i) — печатает число и пробел.
  • Второй printf("\n") — перевод строки после цикла.
$ gcc prog.c -o prog
$ ./prog
Hello, World!
2 + 3 = 5
Числа от 1 до 5: 1 2 3 4 5 

$ git add prog.c
$ git commit -m "Добавить цикл вывода чисел"
[main 7c8d9e0] Добавить цикл вывода чисел
 1 file changed, 10 insertions(+)
Важно: этот хеш — последний «хороший»

Коммит с сообщением «Добавить цикл вывода чисел» — последний, в котором программа работала правильно. На него мы будем перемещаться в разделе 10. Хеш 7c8d9e0 — пример. Ваш собственный Вы найдёте в git log или прямо в выводе git commit выше. Запишите его сейчас, пока он перед глазами.

Состояние: три коммита. Программа полностью работает.

8. Коммит 4: ошибочное «улучшение»

Намеренно сделаем ошибку — так, как это часто бывает: «оптимизировали» sum и случайно заменили сложение на умножение.

Шаг 9. Внести баг

В функции sum меняем a + b на a * b.

int sum(int a, int b) {
    return a * b;  // ОШИБКА: должно быть a + b
}
$ gcc prog.c -o prog
$ ./prog
Hello, World!
2 + 3 = 6
Числа от 1 до 5: 1 2 3 4 5 

$ git add prog.c
$ git commit -m "Оптимизировать sum"
[main 3f2a1b7] Оптимизировать sum
 1 file changed, 1 insertion(+), 1 deletion(-)

Состояние: четыре коммита. Программа работает, но с багом. Хеш 3f2a1b7 — пример, у Вас другой.

9. Смотрим историю и выписываем свои хеши

Шаг 10. git log — все коммиты

$ git log --oneline
3f2a1b7 (HEAD -> main) Оптимизировать sum
7c8d9e0 Добавить цикл вывода чисел
e4f5a6b Добавить функцию sum и вывод её результата
a1b2c3d Добавить Hello World на C
Разбор команды
  • git log — история коммитов.
  • --oneline — по одной строке: сокращённый хеш + сообщение.
Это пример вывода!

Хеши 3f2a1b7, 7c8d9e0, e4f5a6b, a1b2c3d — из учебника, не из Вашего репозитория. У Вас в терминале будут свои. Если Вы скопируете команду с этими хешами — Git ответит fatal: bad revision. Внимательно посмотрите на свой вывод.

Наблюдение: подозрительный коммит — «Оптимизировать sum». Именно после него появился баг. Последний «хороший» — «Добавить цикл вывода чисел».

Шаг 11. Выпишите свои хеши — это обязательно

Прежде чем идти дальше, составьте личную шпаргалку. Без неё следующие шаги делать неудобно.

Возьмите лист бумаги, откройте заметки — или прямо здесь, в этом документе, если читаете с возможностью правок — выпишите хеши из своего вывода git log --oneline. Сопоставьте каждое сообщение с хешем, который Вы видите у себя.

✍️ Мои хеши — заполните сами

В правом столбце вместо прочерков впишите свои хеши из git log --oneline. В левом — сообщения, чтобы не перепутать.

Сообщение коммита Мой хеш (7 символов)
Добавить Hello World на C ____________
Добавить функцию sum и вывод её результата ____________
Добавить цикл вывода чисел ← «последний хороший» ____________
Оптимизировать sum ← «плохой, с багом» ____________
Зачем это нужно

В следующих шагах Вам нужно будет подставлять конкретные хеши в команды. Если Вы будете брать их из учебника — они не сработают. Своя шпаргалка — единственный способ спокойно пройти практику. Если потеряете — не страшно, всегда можно снова выполнить git log --oneline.

Готово: у Вас есть четыре своих хеша. Дальше — только они.

Шаг 12. Посмотреть подозрительный коммит

Увидеть, что именно поменялось в коммите, где впервые появился баг.

Замените хеш на свой

В команде ниже 3f2a1b7 — пример. Подставьте свой хеш коммита «Оптимизировать sum» из Вашей шпаргалки. Если забыли — найдите командой git log --oneline --grep="Оптимизировать". 

$ git show ВАШ_ХЕШ_ОПТИМИЗИРОВАТЬ_SUM
commit 3f2a1b7...
Author: Иван Иванов <ivan@example.com>
Date:   Mon Oct 20 15:01:23 2026 +0300

    Оптимизировать sum

diff --git a/prog.c b/prog.c
@@ -3,7 +3,7 @@
 int sum(int a, int b) {
-    return a + b;
+    return a * b;
 }
Разбор команды
  • git show <хеш> — показывает подробности коммита: автора, дату, сообщение и diff относительно предыдущего.
  • Вам нужно подставить свой хеш.
Разбор вывода
Что вывел Git (пример)
commit 3f2a1b7...
Полный хеш Вашего коммита (у Вас другой).

Строка со знаком - — была в предыдущей версии, стала удалена.
+ return a * b;
Строка со знаком + — добавлена в этой версии. Вот баг.

Вывод: баг подтверждён. Теперь хочется посмотреть, как было «до».

10. Перемещаемся на старый коммит

Главный шаг практики: переместить рабочую папку на коммит «Добавить цикл вывода чисел» — последний «хороший». Файлы на диске заменятся на те, что были в тот момент. Ничего не потеряется: последний коммит по-прежнему в истории.

Что такое detached HEAD

В обычном состоянии HEAD указывает на ветку (main), а ветка — на коммит. Когда Вы перемещаетесь на конкретный коммит «в обход» ветки, HEAD начинает указывать прямо на коммит. Это состояние называется detached HEAD («отсоединённый HEAD»). Оно нормальное и безопасное для просмотра и компиляции. Опасность только одна: если в этом состоянии сделать новый коммит и потом уйти — этот коммит «потеряется», потому что на него не указывает ни одна ветка. Поэтому: в detached HEAD можно смотреть, компилировать, экспериментировать — но не коммитить, если не собираетесь создать ветку (об этом в разделе 15).

Шаг 13. Переместиться на «Добавить цикл вывода чисел»

Рабочая папка откатывается к состоянию третьего коммита.

Найдите свой хеш

В команде ниже 7c8d9e0 — пример. Подставьте свой хеш коммита «Добавить цикл вывода чисел» из Вашей шпаргалки. Если забыли — найдите: git log --oneline --grep="цикл". Именно этот шаг чаще всего ломается, если скопировать хеш из учебника — не делайте так.

Можно осматриваться, экспериментировать, даже коммитить, но при переключении на ветку такие коммиты потеряются.
If you want to create a new branch...
Подсказка про git switch -c. К этому вернёмся в разделе 15.
Or undo this operation with: git switch -
Быстрый возврат на предыдущую позицию — одной командой.
HEAD is now at 7c8d9e0 Добавить цикл вывода чисел
Итог: HEAD на нужном коммите. У Вас тут будет ваш хеш.

Состояние: рабочая папка откатилась на версию третьего коммита. Ветка main и все четыре коммита по-прежнему живы в истории.

Шаг 14. Проверить, что мы действительно на старом коммите

$ git status
HEAD detached at 7c8d9e0
nothing to commit, working tree clean

$ cat prog.c
...
int sum(int a, int b) {
    return a + b;   ← снова правильная версия
}
...

Наблюдение: в файле prog.c — снова return a + b;. Бага здесь нет, потому что мы откатились на версию до ошибочного коммита.

11. Компилируем старую версию

Шаг 15. Компиляция старой версии

$ gcc prog.c -o prog
$ ./prog
Hello, World!
2 + 3 = 5
Числа от 1 до 5: 1 2 3 4 5

Вывод: на коммите «Добавить цикл» программа выдаёт 2 + 3 = 5 — правильный результат. Баг появился именно в следующем коммите.

12. Возвращаемся на main

Возвращаемся к самой свежей версии — на ветку main. Рабочая папка снова поменяется: файл prog.c станет тем, что было в последнем коммите (с багом).

Шаг 16. Вернуться на main

$ git switch main
Previous HEAD position was 7c8d9e0 Добавить цикл вывода чисел
Switched to branch 'main'

$ git status
On branch main
nothing to commit, working tree clean

$ ./prog
Hello, World!
2 + 3 = 6   ← снова баг
Числа от 1 до 5: 1 2 3 4 5
Быстрый возврат

Если Вы только что были в detached HEAD и хотите вернуться назад в него, используйте git switch -. Дефис означает «предыдущее положение». То же самое работает и между двумя ветками.

Состояние: снова на main, с багом. История цела, рабочая папка clean.

13. Сравниваем коммиты

Diff внутри одного коммита мы видели (git show). А можно сравнить любые два коммита между собой, не переключаясь ни на один. Полезно, когда хочется понять, «что изменилось с тех пор».

Шаг 17. Сравнить хороший и плохой коммиты

Увидеть ровно те изменения, которые внесли баг.

Оба хеша — свои

В команде ниже 7c8d9e0 — «Добавить цикл» (хороший), 3f2a1b7 — «Оптимизировать sum» (плохой). Оба замените на свои. Порядок важен: сначала «старый», потом «новый». 

$ git diff ВАШ_ХЕШ_ЦИКЛА ВАШ_ХЕШ_ОПТИМИЗИРОВАТЬ
diff --git a/prog.c b/prog.c
@@ -3,7 +3,7 @@
 int sum(int a, int b) {
-    return a + b;
+    return a * b;
 }
Разбор команды
  • git diff <хеш1> <хеш2> — сравнивает два коммита. хеш1 = «старый», хеш2 = «новый».
  • То, что было в первом коммите, но не во втором — со знаком -; то, что появилось во втором — со знаком +.
  • Если поменять местами — + и - поменяются ролями.

Наблюдение: между «хорошим» и «плохим» коммитом изменение ровно одно — замена + на *.

Шаг 18. Сравнить первый и последний коммиты

$ git diff ВАШ_ХЕШ_HELLO ВАШ_ХЕШ_ОПТИМИЗИРОВАТЬ --stat
 prog.c | 16 +++++++++++++++-
 1 file changed, 15 insertions(+), 1 deletion(-)

Наблюдение: за четыре коммита файл вырос на 15 строк и потерял одну — ту самую a + b, которая стала a * b.

14. Исправляем баг

Исправим баг и закоммитим исправление отдельным коммитом. Это правильный подход: история не переписывается, багфикс виден отдельной записью.

Шаг 19. Исправить код

Вернуть a + b вместо a * b.

Откройте prog.c и поменяйте строку в функции sum:

int sum(int a, int b) {
    return a + b;  // исправлено
}
$ gcc prog.c -o prog
$ ./prog
Hello, World!
2 + 3 = 5
Числа от 1 до 5: 1 2 3 4 5

Состояние: 2 + 3 = 5 — правильно. Изменения в рабочей папке, но не в индексе.

Шаг 20. Закоммитить исправление

$ git add prog.c
$ git commit -m "Исправить sum: вернуть сложение вместо умножения"
[main 9d1e4c2] Исправить sum: вернуть сложение вместо умножения
 1 file changed, 1 insertion(+), 1 deletion(-)

$ git log --oneline
9d1e4c2 (HEAD -> main) Исправить sum: вернуть сложение вместо умножения
3f2a1b7 Оптимизировать sum
7c8d9e0 Добавить цикл вывода чисел
e4f5a6b Добавить функцию sum и вывод её результата
a1b2c3d Добавить Hello World на C

Готово: в истории пять коммитов. Плохой коммит не исчез — он остался рядом с исправлением. Это правильно: через полгода будет понятно, когда и как был внесён баг и когда исправлен.

Альтернатива: git revert

Можно было бы выполнить git revert ВАШ_ХЕШ_ОПТИМИЗИРОВАТЬ — Git сам создал бы коммит-исправление, возвращающий a + b. Результат тот же, но код руками Вы бы не писали. Плюс revert работает, даже если баг в коммите был сложным, из нескольких файлов.

15. Бонус: ветка из старого коммита

Часто бывает: Вы смотрите старый коммит в detached HEAD и понимаете, что хотите не просто «посмотреть», а сделать от него отдельную линию. Для этого из detached HEAD нужно создать ветку.

Шаг 21. Создать ветку из «Добавить цикл»

Снова свой хеш

7c8d9e0 — пример. Подставьте свой хеш коммита «Добавить цикл вывода чисел». 

$ git switch --detach ВАШ_ХЕШ_ЦИКЛА
...
HEAD is now at 7c8d9e0 Добавить цикл вывода чисел

$ git switch -c experiment-without-bug
Switched to a new branch 'experiment-without-bug'

$ git log --oneline --graph --all
* 9d1e4c2 (main) Исправить sum: вернуть сложение вместо умножения
* 3f2a1b7 Оптимизировать sum
* 7c8d9e0 (HEAD -> experiment-without-bug) Добавить цикл вывода чисел
* e4f5a6b Добавить функцию sum и вывод её результата
* a1b2c3d Добавить Hello World на C
Разбор команд
  • git switch --detach ВАШ_ХЕШ_ЦИКЛА — снова на старый коммит.
  • git switch -c experiment-without-bug — создаёт новую ветку с этим именем и сразу переключается на неё. Флаг -c = create. Теперь мы не в detached HEAD: HEAD указывает на новую ветку, а она — на тот же коммит.
  • git log --oneline --graph --all — история всех веток с графом.

Что получили: две ветки, растущие из общего коммита. main содержит баг и его исправление, experiment-without-bug — «чистую» линию без бага. Это и есть настоящая сила Git.

16. Если Git ругается: fatal: bad revision

Самая частая ошибка при прохождении этой практики — скопировать команду с хешем из учебника и выполнить. Git ответит: 

$ git switch --detach 7c8d9e0
fatal: bad revision '7c8d9e0'
Что это значит
fatal:
«Фатальная ошибка» — команда не выполнена.
bad revision '7c8d9e0'
«Плохая ревизия» — в Вашем репозитории нет коммита с таким хешем. Git не нашёл его в истории.

16.1. Что делать

  1. Выполните git log --oneline — посмотрите свои хеши.
  2. Найдите строку с нужным сообщением («Добавить цикл вывода чисел», «Оптимизировать sum» и т.п.).
  3. Возьмите первые 7 символов слева от сообщения — это и есть нужный хеш.
  4. Повторите команду, подставив свой хеш.

16.2. Другие полезные ошибки

СообщениеЧто значитЧто делать
fatal: bad revision '...' Такого коммита нет. Проверить хеш через git log --oneline.
fatal: ambiguous argument '...' Хеш слишком короткий или содержит опечатку. Взять хотя бы 7 символов из git log.
error: Your local changes ... would be overwritten by switch В рабочей папке есть незакоммиченные изменения, которые переключение уничтожит. Либо закоммитить (git add ... && git commit), либо отменить (git restore .), либо спрятать (git stash — в следующих главах).
fatal: not a git repository Терминал открыт вне репозитория. cd в папку проекта.
Главное

Ошибка fatal: bad revision ничего не ломает. Git просто отказался выполнять команду. Ваши файлы, история и рабочая папка — в полном порядке. Замените хеш и попробуйте ещё раз.

17.3. Задания для самостоятельной работы

Попробуйте выполнить, не подглядывая. Если что-то не получается — вернитесь к нужному шагу.

  1. Расширьте программу. Добавьте функцию int multiply(int a, int b) и вызов в main. Сделайте отдельный коммит. Запишите его хеш.
  2. Найдите по сообщению. Выполните git log --oneline --grep="multiply". Сколько коммитов нашлось?
  3. Переместитесь на второй коммит (с функцией sum, до цикла). Скомпилируйте и запустите — убедитесь, что print_numbers в нём нет. Используйте свой хеш.
  4. Вернитесь на main. Какая команда это делает?
  5. Сравните второй и последний коммиты через git diff <хеш2> <последний>. Сколько функций появилось?
  6. Создайте ветку clean-version из коммита «Добавить цикл». Переключитесь на неё, добавьте функцию multiply, сделайте коммит. Теперь у Вас две ветки с разными функциями.
  7. Вернитесь на main и убедитесь, что функции multiply здесь нет — она только в ветке clean-version.
  8. Нарочно ошибетесь. Выполните git switch --detach deadbeef. Прочитайте сообщение об ошибке. Объясните сами себе, что оно значит, и исправьте ошибку.

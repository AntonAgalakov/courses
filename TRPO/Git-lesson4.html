Глава 4

Ветки: создание и слияние

Ветка — это самая мощная и самая простая идея Git. Мы научимся создавать ветки, переключаться между ними, делать на них коммиты и сливать обратно в main. Вы увидите оба способа переключения — современный git switch и классический git checkout.

1. Введение

До сих пор мы работали на одной ветке — main. Каждый коммит добавлялся прямо в неё, и это было нормально, пока проект был простой. Но представим типичную ситуацию:

  • В main — рабочая версия программы, которая всех устраивает.
  • Хочется добавить новую функцию, но эксперимент может не удаться.
  • Хочется, чтобы main всё это время оставался рабочим.

Ветки решают эту задачу: можно попробовать новую идею на отдельной ветке, не трогая main. Если получилось — слить обратно. Если нет — выбросить ветку, и main останется нетронутым.

Хорошая новость: ветки в Git — это очень просто. Ветка — это всего лишь указатель на коммит. Не копия файлов, не отдельный каталог — просто «стикер» с именем, приклеенный к одному коммиту. Поэтому создание ветки мгновенное и не занимает места, даже если в проекте тысячи файлов.

Про хеши в этой главе

В схемах и в примерах вывода будут встречаться хеши вроде a1b2c3d. Это примеры — у Вас они будут свои. Но главное: в командах этой главы используются имена веток, а не хеши, поэтому команды можно копировать и вставлять безопасно.

Про switch и checkout

В этой главе для переключения веток мы будем использовать git switch — современную (с 2019 года) команду. Но Вы наверняка встретите и git checkout — он появился гораздо раньше и до сих пор жив. В разделе 5 мы подробно разберём оба и составим таблицу соответствий. Обе команды работают, обе правильные.

2. Что такое ветка

Прежде чем вводить команды, важно понять одну вещь, которая снимает 90% путаницы:

Ветка — это указатель на коммит. Не папка, не копия файлов, не «параллельная вселенная». Просто имя, которое ссылается на конкретный коммит.

Рис. 1. В начале проекта есть только одна ветка main, которая указывает на единственный коммит. HEAD — «Вы сейчас здесь».

Что означает «указатель на коммит»? Вот что:

  • Ветка не хранит файлы. Файлы хранит коммит, на который она указывает.
  • Создание новой ветки не копирует проект. Просто появляется второе имя, указывающее на тот же коммит.
  • Когда Вы делаете коммит, указатель текущей ветки сдвигается на новый коммит. Остальные ветки стоят на месте.

2.1. Создание ветки: что происходит

Вот что происходит при выполнении git switch -c feature (или git checkout -b feature — разницы нет):

Рис. 2. После создания ветки feature есть две ветки, но обе указывают на один и тот же коммит. Файлы физически не скопированы — их и так один экземпляр.

2.2. Коммит на ветке: что происходит

Если теперь на ветке feature сделать коммит — сдвинется только указатель feature:

Рис. 3. Ветка feature ушла вперёд, а main остался на прежнем коммите. Стрелка означает «родитель»: коммит abc1234 указывает на a1b2c3d. Теперь abc1234 существует только в контексте ветки feature.

Именно поэтому, переключившись обратно на main, Вы не увидите нового коммита в git log, а в файлах — новых правок: рабочая папка «перематывается» к тому состоянию, на которое указывает текущая ветка.

2.3. Слияние: что происходит

Когда Вы делаете git merge feature, находясь на main, Git смотрит: «куда указывает feature?» — и если main не сдвигался со своего места, просто передвигает указатель main туда же, куда указывает feature. Всё. Обе ветки снова вместе.

Рис. 4. После слияния обе ветки указывают на один и тот же коммит abc1234. Никаких копий, никаких новых коммитов — просто передвинулся указатель main. Это называется fast-forward (быстрая перемотка).

Почему «слияние» — это не страшно

В простейшем случае (fast-forward) слияние вообще не создаёт новых коммитов и не трогает файлы — просто двигает указатель. Более сложный случай, когда main тоже ушёл вперёд, мы разберём в разделе 7.

3. Как смотреть ветки: git branch

Первая команда для работы с ветками — git branch. Она выводит список веток в репозитории.

3.1. Синтаксис и вывод

$ git branch
* main
Разбор команды
  • git branch — без аргументов: показать список веток.
  • У текущей ветки стоит звёздочка *.
Разбор вывода
Что вывел Git
* main
Единственная ветка в репозитории. Звёздочка означает, что Вы сейчас на ней.

3.2. Когда веток несколько

$ git branch
  feature-second-line
* main

Здесь две ветки: feature-second-line и main. Звёздочка у main — Вы сейчас на ней.

3.3. Дополнительные сведения: git branch -v

$ git branch -v
  feature-second-line abc1234 Добавить вторую строку
* main               abc1234 Добавить вторую строку

Обе ветки на одном коммите abc1234. Если они разойдутся, хеши будут разные — это сразу станет видно.

4. Как создавать и переключаться

Для создания ветки в современном Git используется git switch с флагом -c. Одна команда — и создаёт ветку, и переключается на неё.

4.1. Создать и сразу переключиться

$ git switch -c feature-second-line
Switched to a new branch 'feature-second-line'
Разбор команды
  • git switch — команда переключения между ветками.
  • -c — флаг create: создать новую ветку.
  • feature-second-line — имя новой ветки. Без пробелов, лучше латиницей: feature-login, fix-typo.
Разбор вывода
Что вывел Git
Switched to a new branch 'feature-second-line'
«Переключился на новую ветку feature-second-line». Одна строка говорит сразу о двух действиях: ветка создана и Вы на неё перешли.

4.2. Переключиться на существующую ветку

$ git switch main
Switched to branch 'main'
  • git switch — команда переключения.
  • main — имя существующей ветки.
  • Без -c — если ветки нет, Git выдаст ошибку.
Незакоммиченные изменения при переключении

Если в рабочей папке есть незакоммиченные изменения и Вы переключаетесь на ветку, где эти же файлы отличаются — Git откажется переключаться и предупредит, что изменения будут уничтожены. Решение: закоммитить или отменить изменения (git restore ...).

5. switch и checkout: два способа

Это важно понять один раз и запомнить на всю жизнь: у Git есть две команды для переключения между ветками, и они делают одно и то же.

5.1. Немного истории

До 2019 года для переключения веток использовалась только одна команда — git checkout. Она умела делать сразу несколько разных вещей:

  • переключать ветки;
  • создавать ветки и сразу переключаться на них;
  • восстанавливать файлы (отменять изменения);
  • перемещаться на конкретный коммит (detached HEAD).

Из-за этого checkout было легко перепутать: например, git checkout my-file.txt отменяет изменения в файле, а git checkout my-branch переключает на ветку — синтаксис похожий, а действия совершенно разные. Чтобы убрать путаницу, в Git 2.23 (2019 год) команду checkout разделили на две:

  • git switch — только переключение веток;
  • git restore — только восстановление файлов.

При этом сам checkout никуда не исчез. Он работает, как раньше, и используется по сей день.

5.2. Таблица соответствий

Что нужно сделать Современный способ (switch) Классический способ (checkout)
Переключиться на существующую ветку git switch main git checkout main
Создать ветку и сразу переключиться git switch -c new-feature git checkout -b new-feature
Перейти на конкретный коммит (detached HEAD) git switch --detach <хеш> git checkout <хеш>
Вернуться на предыдущую позицию git switch - git checkout -
Заметили разницу?

В современных командах создание ветки — это switch -c (create), а в классических — checkout -b (branch). Это самая частая точка путаницы: «c» против «b». Просто запомните обе буквы.

5.3. Что выбрать

В этом учебнике мы используем git switch, потому что:

  • это современный стандарт;
  • он делает только одно — переключает ветки, и его невозможно перепутать с отменой правок в файле;
  • если Вы его случайно наберёте с именем файла вместо ветки — Git сразу скажет, что такой ветки нет, и ничего не сломает.

Но git checkout знать нужно обязательно: Вы встретите его в документации, в интернете, в командах коллег. И если однажды увидите git checkout -b my-feature — Вы уже знаете, что это то же самое, что git switch -c my-feature.

5.4. Одна тонкость: checkout умеет ещё и файлы

У checkout есть возможность, которой у switch нет: восстанавливать файлы. Команда 

$ git checkout notes.txt

отменяет все незакоммиченные изменения в файле notes.txt. В современном Git для этого есть отдельная команда git restore notes.txt — она делает ровно то же самое. А вот git switch notes.txt не сработает — switch не работает с файлами.

Итого

git switch = «переключение веток» (только это).
git restore = «восстановление файлов» (только это).
git checkout = «и то, и другое» — старая команда, которая делает обе работы.

6. Практика 1: fast-forward merge

Сценарий: создадим проект с одним файлом, сделаем на нём ветку, добавим изменение, сольём обратно в main. Каждый шаг сопровождается схемой — где сейчас ветки.

Шаг 1. Создать проект

Пустая папка, git init, один файл и первый коммит.

$ mkdir branches-practice
$ cd branches-practice
$ git init
Initialized empty Git repository in /home/user/branches-practice/.git/

$ echo "Первая строка" > notes.txt
$ git add notes.txt
$ git commit -m "Начальный коммит"
[main (root-commit) a1b2c3d] Начальный коммит
 1 file changed, 1 insertion(+)
 create mode 100644 notes.txt
Разбор команд
  • mkdir branches-practice — создаём папку проекта.
  • cd branches-practice — заходим в неё.
  • git init — превращаем в репозиторий.
  • echo "Первая строка" > notes.txt — создаём файл с одной строкой.
  • git add notes.txt — файл в индекс.
  • git commit -m "Начальный коммит" — первый коммит.

Состояние: одна ветка main, один коммит.

Шаг 2. Проверить, на какой ветке Вы

Убедиться, что Вы на main и других веток нет.

$ git branch
* main

Схема:

Шаг 3. Создать ветку и переключиться на неё

Создаём ветку feature-second-line.

$ git switch -c feature-second-line
Switched to a new branch 'feature-second-line'

$ git branch
  main
* feature-second-line
Разбор команд
  • git switch -c feature-second-line — создаёт ветку и сразу переключается.
  • git branch — проверяем: теперь две ветки, звёздочка у новой.
Эквивалент через checkout

То же самое делает git checkout -b feature-second-line. Обратите внимание на -b вместо -c.

Схема: обе ветки смотрят на один и тот же коммит.

Шаг 4. Сделать коммит на новой ветке

Добавляем вторую строку и коммитим — только на ветке.

$ echo "Вторая строка" >> notes.txt
$ cat notes.txt
Первая строка
Вторая строка

$ git add notes.txt
$ git commit -m "Добавить вторую строку"
[feature-second-line abc1234] Добавить вторую строку
 1 file changed, 1 insertion(+)

$ git log --oneline
abc1234 (HEAD -> feature-second-line) Добавить вторую строку
a1b2c3d Начальный коммит

Схема: ветка feature-second-line ушла вперёд, main стоит на месте.

Шаг 5. Переключиться на main — и увидеть, что коммита здесь нет

Главный «щелчок» в понимании веток.

$ git switch main
Switched to branch 'main'

$ cat notes.txt
Первая строка

$ git log --oneline
a1b2c3d (HEAD -> main) Начальный коммит
Эквивалент через checkout

git checkout main — тот же самый результат.

Разбор команд
  • git switch main — переключаемся на main.
  • cat notes.txt — вторая строка исчезла! Рабочая папка «перемоталась» к состоянию main.
  • git log --oneline — история main. Коммита abc1234 здесь нет — он в ветке feature-second-line.

Схема: HEAD вернулся на main, но main стоит на старом коммите.

Шаг 6. Слить ветку в main (fast-forward)

$ git merge feature-second-line
Updating a1b2c3d..abc1234
Fast-forward
 notes.txt | 1 +
 1 file changed, 1 insertion(+)
merge одинаков в обоих способах

git merge — одна команда и для switch, и для checkout.

Разбор вывода
Что вывел Git
Updating a1b2c3d..abc1234
«Обновляю с a1b2c3d до abc1234».
Fast-forward
Быстрая перемотка. Новый коммит не создаётся — main просто передвигается на коммит, где уже стоит ветка.
notes.txt | 1 +
Добавлена одна строка в notes.txt.

Схема: main перескочил на тот же коммит, на котором стоит feature-second-line.

Шаг 7. Проверить результат слияния

$ cat notes.txt
Первая строка
Вторая строка

$ git log --oneline --graph --all
* abc1234 (HEAD -> main, feature-second-line) Добавить вторую строку
* a1b2c3d Начальный коммит

Готово: содержимое ветки теперь в main. Дальше — уберём саму ветку за ненадобностью.

7. Практика 2: три-стороннее слияние

Fast-forward — самый простой случай. Но часто main тоже уходит вперёд, пока Вы работаете на ветке. Тогда Git не может просто передвинуть указатель — у main есть свои коммиты, у ветки свои, и их нужно объединить. Git создаёт специальный коммит слияния, у которого два родителя.

Шаг 1. Создать новую ветку и сделать на ней коммит

Ветка feature-add-config добавляет новый файл config.txt.

$ git switch -c feature-add-config
Switched to a new branch 'feature-add-config'

$ echo "some config" > config.txt
$ git add config.txt
$ git commit -m "Добавить config.txt"
[feature-add-config def8888] Добавить config.txt
 1 file changed, 1 insertion(+)
 create mode 100644 config.txt

Схема: main остался на abc1234, ветка feature-add-config ушла на один коммит вперёд.

Шаг 2. Переключиться на main и сделать там другой коммит

Главное отличие от прошлого сценария: main тоже уходит вперёд.

$ git switch main
Switched to branch 'main'

$ echo "Третья строка" >> notes.txt
$ git add notes.txt
$ git commit -m "Добавить третью строку"
[main ghi7777] Добавить третью строку
 1 file changed, 1 insertion(+)

Схема: ветки разошлись от общего предка abc1234 — у каждой свой коммит сверху.

Шаг 3. Слить ветку в main — теперь это три-стороннее слияние

Git создаст merge-коммит с двумя родителями.

$ git merge feature-add-config -m "Слить feature-add-config в main"
Merge made by the 'ort' strategy.
 config.txt | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 config.txt
Разбор команды
  • git merge feature-add-config — слить ветку feature-add-config в текущую (main).
  • -m "..." — сообщение для коммита слияния. Здесь создаётся новый коммит, поэтому нужно сообщение.
Разбор вывода
Что вывел Git
Merge made by the 'ort' strategy.
«Слияние выполнено стратегией ort». Слово Fast-forward здесь не появляется — это не fast-forward.
config.txt | 1 +
Изменения из ветки: добавлен config.txt с одной строкой.

Схема: появился merge-коммит jkl9999 с двумя родителями — ghi7777 (из main) и def8888 (из feature).

Шаг 4. Посмотреть граф слияния

$ git log --oneline --graph --all
*   jkl9999 (HEAD -> main) Слить feature-add-config в main
|\
| * def8888 (feature-add-config) Добавить config.txt
* | ghi7777 Добавить третью строку
|/
* abc1234 Добавить вторую строку
* a1b2c3d Начальный коммит
Как читать граф
* jkl9999 (HEAD -> main) Слить feature-add-config в main
Самый свежий коммит — merge-коммит. Два пробела после * и |\ ниже — знак того, что у него два родителя.
|\
Граф «раздваивается» — отсюда начинается различие двух веток.
| * def8888 (feature-add-config) Добавить config.txt
Коммит из ветки feature-add-config. Левая колонка — main, правая — ветка.
* | ghi7777 Добавить третью строку
Коммит из main.
|/
Граф «сливается» обратно — обе линии идут к общему предку.
* abc1234 Добавить вторую строку
Общий предок — место, где ветка ответвилась.

Готово: обе линии истории соединены merge-коммитом.

8. Удаление ветки

После слияния ветка больше не нужна — её работа выполнена, а вся история теперь в main. Ветку можно удалить: коммиты, на которые она указывала, никуда не исчезнут.

8.1. Удалить смёрженную ветку

$ git branch -d feature-second-line
Deleted branch feature-second-line (was abc1234).
Разбор команды
  • git branch -d — удалить ветку (-d от delete).
  • feature-second-line — имя ветки, которую удаляем.
  • У branch нет «второй версии» в checkout. Удаление ветки — только через git branch -d.

8.2. Что не получится

Попытка удалить текущую ветку

$ git branch -d main
error: Cannot delete branch 'main' checked out at '/home/user/branches-practice'

Нельзя удалить ветку, на которой сейчас находитесь. Переключитесь на другую и удалите main уже с неё.

Попытка удалить несмёрженную ветку

$ git branch -d feature-unmerged
error: The branch 'feature-unmerged' is not fully merged.
If you are sure you want to delete it, run 'git branch -D feature-unmerged'.

Git не даёт удалить ветку, коммиты которой ещё не вошли в main. Если уверены — заглавная -D: 

$ git branch -D feature-unmerged
Deleted branch feature-unmerged (was xyz0000).
-D — это принудительно

-D удаляет ветку, даже если её коммиты никуда не вошли. Это может привести к «потере» работы. Используйте -D только когда точно уверены.

9. Про хеши в этой главе

В командах этой главы мы не использовали хеши — только имена веток. Хеши в схемах и в выводе (a1b2c3d, abc1234 и т.д.) — примеры; у Вас они будут свои.

Как читать схемы

Коммит — тёмный прямоугольник с хешем. Стрелка указывает от коммита-потомка на его родителя (тот коммит, из которого он вырос). Бейдж под коммитом — это ветка, которая на этот коммит указывает. Если под одним коммитом два бейджа — обе ветки указывают на него. Фиолетовый коммит — merge-коммит, у него два родителя.

Имена веток — тоже выбирайте свои

Имена feature-second-line и feature-add-config — примеры. Вы можете назвать свои ветки как угодно: my-branch, experiment, add-login. Единственные требования: без пробелов, без кириллицы, без специальных символов кроме - и _.

10. Частые ошибки

Переключение на несуществующую ветку

$ git switch nonexistent
fatal: invalid reference: nonexistent

Ветки nonexistent нет. Проверьте список через git branch. Если хотите создать — добавьте -c. (То же с checkout.)

Забыли переключиться, прежде чем коммитить

Самая частая ошибка новичков: планировали работать на ветке, но забыли переключиться и сделали коммит на main. Проверка перед коммитом: git status показывает в первой строке текущую ветку (On branch ...).

Путаница -c и -b

switch -c и checkout -b — это одно и то же (создать ветку и переключиться). Но флаги разные буквы: c у switch (create), b у checkout (branch). Если перепутать, Git выдаст ошибку «unknown switch».

Слияние в неправильном направлении

git merge X означает «слить X в текущую ветку». Если Вы стоите на ветке, а хотите сливать в main, — сначала git switch main, потом git merge <ветка>.

Удаление несмёрженной ветки

Git защищает от потери работы. Либо сначала слейте ветку, либо используйте -D вместо -d.

Незакоммиченные изменения при переключении

$ git switch other-branch
error: Your local changes to the following files would be overwritten by checkout:
	notes.txt
Please commit your changes or stash them before you switch branches.

В рабочей папке есть незакоммиченные правки, а переключение их «затрёт». Закоммитьте или отмените. Обратите внимание: в сообщении Git говорит «by checkout», даже если Вы выполняли switch — внутри это одна и та же операция.

Попытка использовать switch для файлов

$ git switch notes.txt
fatal: invalid reference: notes.txt

switch умеет только ветки. Для файла — git restore notes.txt (современный способ) или git checkout notes.txt (классический).

Слияние с конфликтом

Если обе ветки меняли один и тот же участок одного и того же файла по-разному, Git создаст конфликт. Слияние приостановится, файлы будут помечены маркерами <<<<<<<, =======, >>>>>>>. Разрешение конфликтов — следующая глава. В этой мы специально строили примеры без конфликтов.

11. Итоги главы

Что нужно вынести из главы 4:

  • Ветка — это указатель на коммит, а не копия файлов.
  • main — обычная ветка, создаётся по умолчанию.
  • git branch — список веток (звёздочка — текущая). -v — с хешами.
  • git switch -c <имя> — создать и переключиться (современный способ).
  • git checkout -b <имя> — то же самое, классический способ.
  • git switch <имя> / git checkout <имя> — переключиться на существующую ветку.
  • git merge <ветка> — слить указанную ветку в текущую.
  • Fast-forward — простейший тип: main «догоняет» ветку, нового коммита нет.
  • Три-стороннее слияние — обе ветки ушли вперёд, создаётся merge-коммит с двумя родителями.
  • git branch -d <имя> — удалить смёрженную ветку. Несмёрженную — только через -D.
  • switch и checkout работают одинаково при переключении веток. checkout — старая команда, switch — новая. У checkout -b вместо -c.
  • checkout умеет ещё и файлы, switch — только ветки.

11.2. Задания для самостоятельной работы

  1. Создайте новый проект (git init, один файл, первый коммит).
  2. Создайте ветку feature-a через switch -c, добавьте строку, закоммитьте.
  3. Переключитесь на main через checkout. Убедитесь, что результат тот же.
  4. Слейте feature-a в main (fast-forward).
  5. Удалите ветку feature-a.
  6. Создайте ветку feature-b через checkout -b, добавьте новый файл, закоммитьте.
  7. Переключитесь на main через switch, добавьте другую строку в старый файл, закоммитьте.
  8. Слейте feature-b в main. Выполните git log --oneline --graph --all — найдите merge-коммит.
  9. Удалите ветку feature-b.
  10. Провокация: попробуйте git switch notes.txt. Прочитайте ошибку. Затем выполните git restore notes.txt — работает. И git checkout notes.txt — тоже работает. Сделайте вывод.

Глава 3

Рабочий цикл и отмена изменений

В главах 1 и 2 Git установлен и настроен, первый коммит сделан. Пора разобраться в ежедневном цикле подробно: что именно показывает status, как читать diff, какие бывают варианты add и commit, как настроить .gitignore и — главное — как безопасно отменять изменения, если что-то пошло не так.

1. Введение

В главе 1 мы прошли минимальный цикл: add → commit. Этого хватает, чтобы сделать первый коммит, но не хватает для ежедневной работы. Как только проект становится чуть сложнее, возникают вопросы:

  • «А что я вообще успел изменить с прошлого коммита?»
  • «Как посмотреть, что попадёт в следующий коммит, до того как его сделаю?»
  • «Я случайно добавил в индекс node_modules — как убрать?»
  • «Забыл файл в коммите — что делать, новый коммит или как-то исправить?»
  • «Как вообще не коммитить мусор вроде логов и секретов?»
  • «Я сделал коммит, а в нём ошибка — как откатить?»

На все эти вопросы отвечает эта глава. Причём сначала мы разберёмся с безопасными инструментами (посмотреть, добавить, закоммитить, настроить .gitignore), а уже потом — с отменой. Отмена — самая «страшная» тема для новичка, и правильно её изучать не первой, а после того, как инструмент стал привычным.

Все команды выполняются в терминале (на Windows — в Git Bash), в том репозитории, где Вы работаете. Продолжаем проект hello-git из главы 1 — если он у Вас есть, откройте его; если нет, создайте новый через git init по примеру из главы 1.

2. git status подробно

git status — самая часто используемая команда Git. Она показывает текущее состояние репозитория: на какой ветке Вы находитесь, какие файлы изменены, что уже в индексе, а что ещё нет. В главе 1 мы видели её в двух-трёх ситуациях; здесь разберём все возможные варианты вывода.

2.1. Все возможные блоки вывода

Вывод git status состоит из заголовка и одного или нескольких блоков — по числу категорий, в которых сейчас есть файлы. Порядок блоков всегда одинаковый.

БлокЧто означаетФайлы в нём
On branch main На какой ветке вы находитесь. —
Your branch is up to date with 'origin/main' Есть ли расхождение с удалённой веткой (появится после подключения к серверу, глава 7). —
Changes to be committed: Файлы, которые находятся в индексе (staging area) и попадут в следующий коммит. те, что добавлены через git add
Changes not staged for commit: Файлы, которые уже отслеживаются, но изменены и пока не добавлены в индекс. изменённые modified, удалённые deleted
Untracked files: Файлы, которые есть в рабочей папке, но ещё ни разу не входили в коммит. новые файлы
nothing to commit, working tree clean Всё закоммичено, изменений нет. Это «здоровое» состояние репозитория. —

2.2. Пример: всё сразу в одном статусе

Допустим, в репозитории четыре файла, и они находятся в разных состояниях. Вывод git status покажет все блоки сразу: 

$ git status
On branch main
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
	new file:   index.html

Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   README.md

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	style.css
	script.js
Разбор вывода
On branch main
Вы на ветке main. Единственная ветка в репозитории, с которой пока работаем.
Changes to be committed:
Файлы, которые попадут в следующий коммит. Здесь — только index.html, потому что его добавили через git add.
new file: index.html
Файл новый: он будет добавлен в историю впервые этим коммитом.
Changes not staged for commit:
Файлы, которые уже отслеживаются Git (были в прошлых коммитах), но сейчас отличаются от последнего снимка — и не добавлены в индекс.
modified: README.md
Файл изменён: он был в прошлом коммите, но в рабочей папке его содержимое теперь другое. Если сейчас сделать git commit, старая версия README.md попадёт в снимок, а новые правки — нет.
Untracked files:
Файлы, которые есть в рабочей папке, но ни разу не входили в коммит. Git их видит, но «не ведёт».
style.css
Новый файл, о котором Git ничего не знает. Чтобы он попал в историю, нужен git add.
script.js
Тоже новый файл, тоже без git add.
Почему подсказки в скобках

Git не только сообщает состояние, но и подсказывает команды. (use "git add <file>..." to update what will be committed) — «используйте git add, чтобы добавить файл к коммиту». (use "git restore --staged <file>..." to unstage) — «используйте git restore --staged, чтобы убрать файл из индекса». Подсказки меняются в зависимости от состояния — их полезно читать.

2.3. «Чистое» состояние

Когда все изменения закоммичены, git status выводит лаконичное сообщение: 

$ git status
On branch main
nothing to commit, working tree clean

Строка working tree clean означает, что рабочая папка полностью соответствует последнему коммиту: изменённых файлов нет, неотслеживаемых нет. Это то состояние, к которому стоит стремиться перед тем, как переключаться на другую задачу.

2.4. Короткий формат: git status -s

Полный вывод информативен, но длинный. Флаг -s (от short) выводит ту же информацию двумя колонками символов — очень удобно, когда файлов много. 

$ git status -s
A  index.html
 M README.md
?? style.css
?? script.js
Как читать двухбуквенный код
A index.html
A в первой колонке = Added (добавлен в индекс). Пробел во второй колонке = в рабочей папке изменений нет. Файл будет в следующем коммите.
 M README.md
Пробел в первой колонке = в индексе файла нет. M во второй = Modified (изменён в рабочей папке, не добавлен в индекс).
?? style.css
?? = untracked. Файл не отслеживается.
?? script.js
Тоже неотслеживаемый.

Возможные символы: M — modified, A — added, D — deleted, R — renamed, ?? — untracked. Если символ стоит в первой колонке — изменение в индексе; если во второй — в рабочей папке.

3. git diff: что именно изменилось

git status говорит, какие файлы изменились. git diff показывает, что именно в них изменилось — построчно. Это следующий шаг после status: сначала смотрим список файлов, потом — их содержимое.

3.1. Три варианта diff

У git diff есть три режима, и их легко перепутать. Различаются они тем, какие две области сравнивают.

Working Directory
рабочая папка
Staging Area
индекс
Repository
последний коммит
git diff рабочая папка ↔ индекс — «что изменено, но ещё не добавлено»
git diff --staged индекс ↔ последний коммит — «что попадёт в следующий коммит»
git diff HEAD рабочая папка ↔ последний коммит — «всё, что изменилось с прошлого коммита»

Рис. 1. Три варианта git diff и что каждый из них сравнивает

Запомнить просто: git diff без флагов — «что я поменял и ещё не добавил». --staged — «что я уже добавил и собираюсь закоммитить». HEAD — «всё, что изменилось с момента последнего коммита, независимо от индекса».

Что такое HEAD

HEAD — это указатель на текущий коммит, тот, на котором Вы сейчас находитесь (подробнее — в главе 1, раздел 9). В контексте git diff HEAD это означает «сравни рабочую папку с тем, что записано в HEAD».

3.2. Как читать вывод diff

Допустим, в файле README.md была одна строка, а Вы дописали вторую. Вот что покажет git diff: 

$ git diff
diff --git a/README.md b/README.md
index 3f2a1b7..9d1e4c2 100644
--- a/README.md
+++ b/README.md
@@ -1 +1,2 @@
 # Мой проект
+Вторая строка
Разбор вывода
diff --git a/README.md b/README.md
Заголовок diff-блока. a/ — «старая» версия файла, b/ — «новая». Оба пути одинаковы, потому что это один и тот же файл, просто до и после правки.
index 3f2a1b7..9d1e4c2 100644
Служебная строка: сокращённые хеши версии «до» (3f2a1b7) и «после» (9d1e4c2), а также режим доступа 100644 (обычный файл). Для нас не критично — можно не читать.
--- a/README.md
«Старая» версия файла. Строки, которые есть в ней и удалены в новой, помечаются ниже знаком -.
+++ b/README.md
«Новая» версия файла. Строки, которые появились, помечаются ниже знаком +.
@@ -1 +1,2 @@
«Хунк» (hunk) — заголовок блока изменений. -1 означает «в старой версии начиная со строки 1 затронута 1 строка». +1,2 означает «в новой версии начиная со строки 1 затронуто 2 строки». Если файл большой, таких блоков будет несколько.
 # Мой проект
Строка с пробелом в начале — контекст. Она одинакова в обеих версиях, но показана, чтобы было понятно, где именно происходит изменение.
+Вторая строка
Строка со знаком + в начале — добавлена в новой версии. Если бы мы что-то удалили, была бы строка со знаком -.

Если бы мы что-то удалили, вывод был бы таким:

$ git diff
diff --git a/README.md b/README.md
@@ -1,2 +1 @@
 # Мой проект
-Вторая строка

Строка с - — удалена в новой версии. В нашем примере удалили строку «Вторая строка».

Мнемоника

В git diff знак + — «добавлено в новой версии», - — «было в старой, стало удалено». Не наоборот: плюс всегда означает «то, что появится после применения изменений».

3.3. Краткая статистика: git diff --stat

Если файлов много и хочется увидеть, где сколько строк изменилось, — флаг --stat: 

$ git diff --stat
 README.md  | 1 +
 index.html | 5 ++---
 style.css  | 2 ++
 3 files changed, 6 insertions(+), 2 deletions(-)
Разбор вывода
README.md | 1 +
В файле одна добавленная строка.
index.html | 5 ++---
В файле 5 изменённых строк: 2 добавлено (++), 3 удалено (---).
style.css | 2 ++
Две добавленные строки.
3 files changed, 6 insertions(+), 2 deletions(-)
Итого: три файла, шесть добавленных строк, две удалённые. Строка index.html показала 5 изменённых строк, но в итоге «добавлений — 2, удалений — 3», что в сумме 5.

3.4. Практический сценарий

Типичный порядок работы с diff — перед git add:

  1. git status — понять, какие файлы затронуты.
  2. git diff — посмотреть изменения в них.
  3. Убедиться, что всё нужное — и ничего лишнего.
  4. git add <файл> — добавить в индекс.
  5. git diff --staged — ещё раз проверить, что именно попадёт в коммит.
  6. git commit -m "...".

Пятый пункт особенно полезен: после add можно ещё раз посмотреть глазами на то, что уйдёт в историю. Если случайно добавили лишнее — убрать (как это сделать — в разделе 7).

4. git add: варианты

git add в базовом виде мы уже знаем: git add <файл> добавляет один файл в индекс. Но у команды есть несколько вариантов, и у каждого — своё назначение.

4.1. Все варианты

КомандаЧто добавляетКогда использовать
git add file.txt Один конкретный файл. Когда нужно добавить только его — самый точный и безопасный вариант.
git add folder/ Всю папку целиком (все файлы внутри, включая вложенные). Когда изменения локализованы в одной папке.
git add . Все файлы и папки из текущей папки и ниже. Когда находитесь в корне проекта и хотите добавить всё сразу.
git add -A Всё из корня репозитория, независимо от того, где Вы находитесь. Когда хотите добавить всё, даже если терминал открыт в подпапке.
git add -u Только уже отслеживаемые файлы: изменённые и удалённые. Новые (untracked) не добавятся. Когда новые файлы добавлять не нужно, а изменения в старых — нужно.
git add *.txt Все файлы в текущей папке с расширением .txt. Когда нужна выборка по шаблону.
git add -p Интерактивный режим: Git показывает по одному «куску» изменений и спрашивает, добавлять его или нет. Когда из десяти правок в файле нужно закоммитить только три.

4.2. git add . и git add -A — в чём разница

Для начинающего разница почти незаметна, потому что обычно терминал открыт в корне проекта. Но разница есть:

  • git add . берёт текущую папку и всё, что в ней.
  • git add -A берёт весь репозиторий, независимо от того, где открыт терминал.

Если терминал в корне — они дадут одинаковый результат. Если Вы внутри подпапки src/ и выполните git add ., добавятся только файлы из src/. А git add -A добавит файлы из всего репозитория. Когда работаете из корня — разницы нет, берите любое.

Осторожно с `git add .`

git add . — самая частая причина «случайно закоммитил мусор» у новичков. Он добавляет всё, включая неотслеживаемые файлы: результаты сборки, логи, временные файлы, .env. Прежде чем выполнять его, убедитесь, что .gitignore настроен (раздел 6) и что git status не показывает ничего лишнего. Если сомневаетесь — добавляйте конкретные файлы явно.

4.3. Что делать, если добавили не то

Это бывает со всеми. Решение — git restore --staged: 

$ git restore --staged node_modules/

Команда убирает указанное из индекса, но не трогает содержимое файла в рабочей папке. После этого файл снова в состоянии «изменён, но не добавлен» (или untracked, если он никогда не коммитился). Подробно — в разделе 8.

5. git commit: варианты

git commit — команда, которая создаёт снимок. В главе 1 мы использовали её с флагом -m. Есть и другие варианты.

5.1. Все варианты

КомандаЧто делает
git commit -m "Сообщение" Стандартный вариант: коммит с сообщением прямо в командной строке. Самый частый.
git commit Открывает редактор для ввода сообщения. Используется, когда сообщение длинное (первая строка + подробное описание).
git commit -am "Сообщение" Сокращение для git add -u && git commit -m: сам добавит в индекс изменённые и удалённые файлы и сразу закоммитит. Новые (untracked) файлы не добавит.
git commit --amend -m "..." Исправляет последний коммит: переписывает сообщение и, если в индексе есть изменения, — добавляет их в тот же коммит. Создаёт новый коммит на месте старого.
git commit --amend --no-edit То же самое, но не трогает сообщение. Удобно, когда забыли добавить файл в последний коммит.

5.2. git commit без -m: редактор

Если запустить git commit без -m, откроется редактор — по умолчанию Vim. Вы увидите примерно такой экран: 

# Please enter the commit message for your changes. Lines starting
# with '#' will be ignored, and an empty message aborts the commit.
#
# On branch main
# Changes to be committed:
#	new file:   hello.txt
#

Верхние строки — заготовка для Вашего сообщения. Строки, начинающиеся с #, — служебные, в сообщение не попадут. Вам нужно:

  1. Написать сообщение в начале файла (над комментариями).
  2. В Vim: нажать Esc, затем набрать :wq и нажать Enter — сохранить и выйти.
  3. Если передумали — Esc, затем :q! и Enter — выйти без сохранения; коммит будет отменён.

Если редактор Vim неудобен — просто всегда используйте -m. Для большинства коммитов этого достаточно: одна строка сообщения умещается прямо в командной строке.

5.3. git commit -am: когда удобно и когда опасно

Флаг -am — это два флага сразу: -a (добавить все отслеживаемые изменения) и -m (с сообщением). Команда: 

$ git commit -am "Исправить опечатку в README"

Работает так: Git сам пройдётся по уже отслеживаемым файлам, добавит их изменения в индекс и сразу закоммитит. Одна команда вместо двух.

Что НЕ попадёт в коммит с -am

Новые (untracked) файлы. Флаг -a работает только с теми файлами, которые Git уже отслеживает (то есть они были хотя бы в одном прошлом коммите). Если Вы создали новый файл, git commit -am его проигнорирует — сначала нужно git add <новый файл>.

5.4. git commit --amend: исправить последний коммит

Ситуация: сделали коммит, а потом поняли, что забыли файл, или в сообщении опечатка. Вместо того чтобы делать новый коммит «сверху», можно переписать последний: 

# вариант 1: исправить только сообщение
$ git commit --amend -m "Более точное сообщение"

# вариант 2: добавить забытый файл в тот же коммит
$ git add forgotten-file.txt
$ git commit --amend --no-edit

Оба варианта создают новый коммит на месте старого — с новым хешем. Старый коммит как бы «исчезает» из истории, а вместо него появляется исправленный.

Не делайте amend для опубликованных коммитов

--amend изменяет историю. Если коммит ещё никуда не отправлялся (git push) — это безопасно. Если он уже на сервере и с ним работают другие люди — amend создаст расхождение, и всем придётся разбираться. Правило: --amend только для локальных коммитов, ещё не запушенных. Про push — в главе 7.

Важно: мы пока не подключали удалённый репозиторий — это будет в главе 7. Все коммиты, которые Вы делаете сейчас, лежат только на Вашем компьютере; «опубликованных» среди них нет, поэтому --amend для них безопасен. Слова про опубликованные коммиты — задел на будущее.

6. .gitignore: что не коммитить

Не все файлы в проекте должны попадать в историю. Типичные примеры:

  • Зависимости — папка node_modules/ в Node.js или venv/ в Python. Они восстанавливаются командой установки, хранить их в Git бессмысленно и тяжело.
  • Результаты сборки — папки dist/, build/, target/. Они генерируются из исходников.
  • Секреты — файлы .env, *.pem, config.local.json. Они не должны попасть в публичный репозиторий.
  • Логи и временные файлы — *.log, *.tmp, .DS_Store (macOS), Thumbs.db (Windows).
  • Настройки редакторов — папка .vscode/, .idea/, если они у каждого свои.

Для всего этого есть файл .gitignore — обычный текстовый файл в корне репозитория, в котором перечислены шаблоны имён. Всё, что совпадает с шаблоном, Git не видит при git add и не показывает в git status.

6.1. Синтаксис

Строка в .gitignoreЧто означает

*.logВсе файлы, оканчивающиеся на .log.

# комментарийСтроки, начинающиеся с #, — комментарии.

6.2. Типичный .gitignore

Вот пример для проекта на Node.js. Для другого стека будут свои строки, но структура та же.

6.3. Как создать и проверить

Создать файл можно любым способом: в редакторе или в терминале. Через терминал — так же, как создавали hello.txt: 

$ echo "node_modules/" > .gitignore
$ echo "*.log" >> .gitignore
$ echo ".env" >> .gitignore

Первая команда создаёт файл .gitignore с первой строкой. Вторая и третья — дописывают ещё две строки. > перезаписывает, >> дописывает.

Проверить, что файл работает: 

$ git status
On branch main
Untracked files:
  (use "git add <file>..." to include in what will be committed)
	.gitignore

В списке untracked появился только .gitignore — но не node_modules/ и не .env, даже если они есть в папке. Это значит, что .gitignore работает: файлы, подходящие под шаблоны, исчезли из git status.

Если хочется проверить конкретно: git status --ignored покажет и игнорируемые файлы тоже (в отдельном блоке).

.gitignore тоже нужно закоммитить

Файл .gitignore — часть проекта. Он должен попасть в репозиторий, чтобы все, кто клонирует проект, получили те же правила игнорирования. Не забудьте git add .gitignore и коммит.

6.4. Особый случай: файл уже отслеживается

.gitignore работает только с файлами, которых Git ещё не знает. Если файл уже был закоммичен раньше, добавление его в .gitignore ничего не даст — Git продолжит его отслеживать.

Чтобы «отвязать» такой файл от Git, но оставить его на диске: 

$ git rm --cached config.json

Флаг --cached означает «удалить из индекса, но не с диска». После этого файл станет обычным untracked — и если он есть в .gitignore, Git про него забудет. Удаление из индекса нужно будет закоммитить: 

$ git commit -m "Убрать config.json из репозитория"

В следующий коммит попадёт «удаление» файла из истории. Сам файл на диске останется.

7. Отмена изменений: большая таблица

Это самая важная часть главы. Если Вы умеете безопасно отменять — Вы перестаёте бояться экспериментировать. А это половина продуктивности в Git.

Важно понимать: в Git нет одной «отменить». Разные ситуации требуют разных команд, и у них разная степень опасности. Вот полная таблица — от самых безопасных к самым опасным.

Что хотите Команда Опасность
Убрать файл из индекса (оставить правки в файле) git restore --staged <файл> безопасно
Отменить правки в файле (вернуть как в последнем коммите) git restore <файл> правки теряются
Исправить сообщение последнего коммита git commit --amend -m "..." только для неопубликованных
Добавить забытый файл в последний коммит git add <файл> && git commit --amend --no-edit только для неопубликованных
Откатить последний коммит, сохранив изменения в индексе git reset --soft HEAD~1 безопасно
Откатить последний коммит, сохранив изменения в рабочей папке git reset HEAD~1 безопасно
Откатить последний коммит и уничтожить изменения git reset --hard HEAD~1 необратимо
Отменить опубликованный коммит (создать «антикоммит») git revert <хеш> безопасно
Про «опубликованные» коммиты

В этой главе мы ещё не подключались к удалённому серверу — это будет в главе 7. Пока все коммиты лежат локально, только на Вашем компьютере, и «опубликованных» среди них нет. Всё, что в таблице и далее сказано про опубликованные коммиты, — задел на будущее: когда появится git push, эти правила станут актуальными.

7.1. Что такое HEAD~1

В нескольких командах выше встречается HEAD~1. Это сокращение означает «на один коммит назад от HEAD». То есть HEAD — последний коммит, HEAD~1 — предпоследний, HEAD~2 — на два назад, и так далее.

git reset HEAD~1 буквально означает «переместить указатель HEAD на один коммит назад». Что при этом произойдёт с файлами — зависит от флага (--soft, --mixed, --hard), см. раздел 8.

7.2. Reset vs revert: в чём принципиальная разница

У этих двух команд разные философии:

  • reset — «перемотать историю назад». Коммит как бы исчезает, будто его не было. Опасно, если коммит уже кто-то скачал.
  • revert — «добавить в конец новый коммит, который отменяет изменения старого». История не переписывается, старый коммит остаётся. Безопасно для любых ситуаций.

Для локальной работы удобнее reset. Для общих веток, где уже кто-то работает, — revert.

8. Разбор каждой команды отмены

Проходим по каждой команде из таблицы и смотрим подробно, что она делает и когда применять.

8.1. git restore --staged <файл> — убрать из индекса

Ситуация: выполнили git add, но передумали — файл не должен попасть в коммит. 

$ git restore --staged config.json
  • restore — команда восстановления файла.
  • --staged — режим «работаем с индексом» (staging area).
  • config.json — файл.

Файл исчезает из индекса, но его содержимое на диске не меняется. Если файл был новым (untracked до git add) — снова становится untracked. Если отслеживаемым — возвращается в состояние «изменён, но не добавлен».

Старый синтаксис

В старых версиях Git и в старых учебниках встречается git reset HEAD <файл> — работает так же. git restore --staged — современный и более понятный вариант.

8.2. git restore <файл> — отменить правки в файле

Ситуация: изменили файл, но поняли, что изменение никуда не годится, хотите вернуть как было в последнем коммите. 

$ git restore hello.txt
  • restore — восстановить.
  • Без флага --staged — работаем с рабочей папкой.
  • hello.txt — файл, который нужно восстановить.
⚠️ Правки теряются безвозвратно

git restore уничтожает все несохранённые правки в файле. Отменить это действие нельзя — Git заменит файл версией из последнего коммита. Если сомневаетесь — сначала git diff, чтобы увидеть, что именно будет потеряно.

8.3. git commit --amend — исправить последний коммит

Уже разобрали в разделе 5.4. Напомню два варианта: 

# только сообщение
$ git commit --amend -m "Новое сообщение"

# добавить забытый файл, сообщение не менять
$ git add forgotten.txt
$ git commit --amend --no-edit

Работает только для последнего коммита и только пока он не запушен. Если коммит уже на сервере — amend перепишет историю, и у других людей возникнет расхождение.

8.4. git reset --soft HEAD~1 — откатить коммит, оставить в индексе

Ситуация: сделали коммит, но поняли, что закоммитили не то (например, слишком много файлов или плохое сообщение), и хотите переделать коммит целиком. 

$ git reset --soft HEAD~1
  • reset — переместить указатель.
  • --soft — мягкий режим: не трогать ни индекс, ни рабочую папку.
  • HEAD~1 — на один коммит назад.

Что происходит: указатель HEAD и текущая ветка откатываются на один коммит назад. Но изменения из отменённого коммита остаются в индексе — как будто Вы их только что выполнили git add. Теперь можно поправить сообщение, убрать лишнее из индекса, добавить недостающее — и сделать новый коммит.

8.5. git reset HEAD~1 — откатить коммит, оставить в рабочей папке

То же самое, но изменения выгружаются в рабочую папку и становятся «не добавленными»: 

$ git reset HEAD~1

Без флага reset работает как --mixed: коммит исчезает, индекс очищается, а изменения файлов остаются на диске. Дальше можно спокойно просматривать их через git diff и решать, что с ними делать.

Разница с --soft: после --soft изменения уже в индексе (можно сразу коммитить), после --mixed — в рабочей папке (нужно снова git add).

8.6. git reset --hard HEAD~1 — откатить и уничтожить

⚠️ Необратимо

git reset --hard HEAD~1 откатывает указатель на один коммит назад и уничтожает все изменения в рабочей папке и индексе. Файлы станут ровно такими, какими были в предыдущем коммите. Восстановить «потерянное» можно только через git reflog, и это уже продвинутая тема. Не используйте --hard, пока не уверены на 100%.

Применяется, когда Вы точно хотите «выбросить» последний коммит и все его изменения, не сохраняя ничего.

8.7. git revert <хеш> — отменить опубликованный коммит

Ситуация: коммит уже отправлен на сервер, его скачали другие, переписывать историю нельзя. Нужно «отменить» его содержимое, не трогая историю. 

$ git revert 3f2a1b7
  • revert — «откатить», но по-другому, чем reset.
  • 3f2a1b7 — хеш коммита, который надо отменить (первые 7 символов достаточно).

Что происходит: Git создаёт новый коммит, который вносит изменения, противоположные указанному коммиту. Если тот коммит добавил строку — revert её удалит. Если удалил файл — revert его вернёт. История не переписывается: старый коммит остаётся, рядом появляется «антикоммит».

Git откроет редактор для сообщения коммита-отмены. По умолчанию там будет что-то вроде «Revert "Добавить приветствие в hello.txt"». Можно согласиться (:wq в Vim) или изменить.

Хеш у Вас будет другой

3f2a1b7 — это пример хеша из учебного репозитория. У Вас хеши будут совершенно другие: они зависят от содержимого коммита, автора, времени и других данных. Не копируйте команду с этим хешем буквально — посмотрите свой хеш через git log --oneline и подставьте его. То же самое касается хешей 9d1e4c2, 4b5c6d7 и любых других в этой главе.

Почему revert безопаснее reset

reset удаляет коммиты из истории — если их кто-то уже скачал, у него останется «лишний» коммит, и синхронизация сломается. revert ничего не удаляет, только добавляет — это всегда безопасно для общих веток. Поэтому в командах действует правило: «в своей локальной ветке — reset, в общей — revert».

Напомню: пока все наши коммиты локальные (см. врезку в разделе 7), поэтому на практике в этой главе revert Вам вряд ли понадобится — он нужен, когда появится удалённый репозиторий в главе 7.

9. Практика: сделал ошибку — исправил

Пройдём сценарий: намеренно сделаем несколько типичных ошибок и исправим каждую. Все команды в терминале, в папке проекта hello-git.

Шаг 1. Исходное состояние

Убедимся, что репозиторий в «чистом» состоянии и есть хотя бы один коммит.

$ git status
On branch main
nothing to commit, working tree clean

$ git log --oneline
9d1e4c2 (HEAD -> main) Добавить вторую строку в hello.txt
3f2a1b7 Добавить приветствие в hello.txt
Разбор вывода
Что вывел Git
nothing to commit, working tree clean
Всё закоммичено, изменений нет. Хорошая отправная точка.
9d1e4c2 (HEAD -> main) ...
Два коммита в истории. HEAD на самом последнем. Хеши 9d1e4c2 и 3f2a1b7 — пример; у Вас они будут другими, смотрите свой вывод git log --oneline.

Состояние: чисто, два коммита в истории.

Шаг 2. Ошибка: изменили файл не туда

Испортим hello.txt — допишем мусорную строку — и отменим правки через git restore.

$ echo "ЭТО МУСОР, НЕ НУЖНО" >> hello.txt
$ git status
On branch main
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   hello.txt

no changes added to commit (use "git add" and/or "git commit -a")

$ git diff
diff --git a/hello.txt b/hello.txt
@@ -1,2 +1,3 @@
 Привет, Git!
 Вторая строка
+ЭТО МУСОР, НЕ НУЖНО

$ git restore hello.txt
$ git status
On branch main
nothing to commit, working tree clean
Разбор команд
  • echo "..." >> hello.txt — дописываем строку в файл.
  • git status — видим, что файл изменён, но не в индексе.
  • git diff — видим сами изменения: добавлена одна строка.
  • git restore hello.txt — откатываем изменения. Файл возвращается к версии из последнего коммита.
  • git status — снова чисто.

Исправлено: мусорная строка удалена, файл в исходном состоянии. Если бы мы сделали git restore не подумав, изменения бы потерялись навсегда — но здесь мы как раз этого и хотели.

Шаг 3. Ошибка: случайно добавили не тот файл в индекс

Создадим «секретный» файл и случайно добавим его в индекс. Уберём через git restore --staged.

$ echo "password=12345" > secret.txt
$ echo "Правка в README" >> README.md
$ git add .
$ git status
On branch main
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
	modified:   README.md
	new file:   secret.txt

$ git restore --staged secret.txt
$ git status
On branch main
Changes to be committed:
	modified:   README.md

Untracked files:
	secret.txt
Разбор команд
  • echo "password=12345" > secret.txt — создаём файл с «секретом». > создаёт новый файл.
  • echo "..." >> README.md — дописываем в README. Это мы хотим закоммитить.
  • git add . — добавляем всё, включая нежелательный secret.txt.
  • git restore --staged secret.txt — убираем secret.txt из индекса. Файл на диске остаётся, просто перестаёт быть подготовленным к коммиту.

Исправлено: в индексе только README.md. secret.txt снова untracked и в коммит не попадёт. Правильный следующий шаг — добавить secret.txt в .gitignore (см. следующий шаг).

Шаг 4. Создадим .gitignore, чтобы это не повторялось

Настроим игнорирование, чтобы secret.txt и подобное больше не попадали в git status.

$ echo "secret.txt" > .gitignore
$ echo "*.log" >> .gitignore
$ git status
On branch main
Changes to be committed:
	modified:   README.md

Untracked files:
	.gitignore
Разбор команд
  • Создаём .gitignore с двумя шаблонами: secret.txt (конкретный файл) и *.log (все логи).
  • git status показывает: secret.txt исчез из списка untracked (его теперь игнорирует Git), а .gitignore появился — его как раз надо закоммитить.

Исправлено: secret.txt больше не попадает в статус. В индексе — README, к коммиту готовы также .gitignore.

Шаг 5. Коммит — но с ошибкой в сообщении

Закоммитим всё правильно, но с плохим сообщением. Исправим через git commit --amend.

$ git add .gitignore README.md
$ git commit -m "asdf"
[main 7c8d9e0] asdf
 2 files changed, 2 insertions(+)
 create mode 100644 .gitignore

$ git commit --amend -m "Добавить .gitignore и обновить README"
[main e1f2a3b] Добавить .gitignore и обновить README
 2 files changed, 2 insertions(+)
 create mode 100644 .gitignore

$ git log --oneline
e1f2a3b (HEAD -> main) Добавить .gitignore и обновить README
9d1e4c2 Добавить вторую строку в hello.txt
3f2a1b7 Добавить приветствие в hello.txt
Разбор команд
  • git add .gitignore README.md — добавляем два файла в индекс. Обратите внимание: secret.txt не добавлен, потому что он в .gitignore.
  • git commit -m "asdf" — коммитим с плохим сообщением. Git выдаёт строку с хешем 7c8d9e0.
  • git commit --amend -m "..." — переписываем последний коммит: сообщение меняется, хеш тоже меняется (становится e1f2a3b). Содержимое коммита остаётся прежним.
  • git log --oneline — убеждаемся: в истории только правильный коммит e1f2a3b, а «asdf» пропал.

Исправлено: сообщение теперь осмысленное. Коммит переписан — важно, что он ещё никуда не отправлялся (мы работаем только локально).

Шаг 6. Ошибка: забыли файл в последнем коммите

Представим, что в предыдущий коммит забыли добавить ещё один файл. Добавим его через --amend --no-edit.

$ echo "Установка: ..." > INSTALL.md
$ git add INSTALL.md
$ git commit --amend --no-edit
[main 4b5c6d7] Добавить .gitignore и обновить README
 3 files changed, 3 insertions(+)
 create mode 100644 .gitignore
 create mode 100644 INSTALL.md

$ git log --oneline
4b5c6d7 (HEAD -> main) Добавить .gitignore и обновить README
9d1e4c2 Добавить вторую строку в hello.txt
3f2a1b7 Добавить приветствие в hello.txt
Разбор команд
  • git add INSTALL.md — добавляем забытый файл в индекс.
  • git commit --amend --no-edit — переписываем последний коммит, добавив в него всё, что сейчас в индексе. Флаг --no-edit означает «не открывай редактор, оставь сообщение как было».
Разбор вывода
Что вывел Git
[main 4b5c6d7] Добавить .gitignore и обновить README
Коммит переписан, новый хеш — 4b5c6d7 (был e1f2a3b). Сообщение осталось тем же.
3 files changed, 3 insertions(+)
Теперь в коммите три файла вместо двух: .gitignore, README.md и INSTALL.md.
create mode 100644 INSTALL.md
Новый файл в коммите. Строки с create mode показывают файлы, созданные этим коммитом.

Исправлено: забытый файл в том же коммите, история по-прежнему из трёх коммитов.

Шаг 7. Ошибка: коммит вообще не нужен

Сделаем «лишний» коммит и откатим его через git reset --soft HEAD~1, сохранив изменения в индексе.

$ echo "Эксперимент" > experiment.txt
$ git add experiment.txt
$ git commit -m "Экспериментальный коммит"
[main 5e6f7a8] Экспериментальный коммит
 1 file changed, 1 insertion(+)
 create mode 100644 experiment.txt

$ git reset --soft HEAD~1

$ git status
On branch main
Changes to be committed:
	new file:   experiment.txt

$ git log --oneline
4b5c6d7 (HEAD -> main) Добавить .gitignore и обновить README
9d1e4c2 Добавить вторую строку в hello.txt
3f2a1b7 Добавить приветствие в hello.txt
Разбор команд
  • Сначала создаём файл experiment.txt, добавляем в индекс и коммитим — как будто это нормальная работа.
  • git reset --soft HEAD~1 — откатываем последний коммит: указатель HEAD и ветка main уходят на один коммит назад. Но изменения остаются в индексе — то есть файл по-прежнему staged.
  • git status показывает: experiment.txt готов к коммиту, но самого коммита в истории уже нет.

Исправлено: «Экспериментальный коммит» исчез из истории, но файл остался в индексе. Теперь можно либо закоммитить его заново, либо убрать через git restore --staged, либо откатить правки через git restore.

Шаг 8. Убираем эксперимент насовсем

Файл experiment.txt нам не нужен. Уберём его из индекса и удалим с диска.

$ git restore --staged experiment.txt
$ rm experiment.txt
$ git status
On branch main
nothing to commit, working tree clean

$ git log --oneline
4b5c6d7 (HEAD -> main) Добавить .gitignore и обновить README
9d1e4c2 Добавить вторую строку в hello.txt
3f2a1b7 Добавить приветствие в hello.txt
Разбор команд
  • git restore --staged experiment.txt — убираем файл из индекса. Теперь он снова untracked.
  • rm experiment.txt — обычное удаление файла с диска (не Git-команда).
  • git status — чисто. Git про файл ничего не знал, поэтому его удаление для Git незаметно.

Готово: эксперимент полностью убран, история в порядке, рабочая папка чиста.

Итог практики

Мы исправили семь типичных ошибок без потери данных и без единого «страшного» действия. Обратите внимание: ни разу не понадобился git reset --hard — и это правильно. В реальной работе --hard нужен очень редко.

10. Частые ошибки

git add . без .gitignore

Самая частая причина «закоммитил node_modules». Файл .gitignore должен появиться в проекте сразу, до первого git add. Если уже закоммитили лишнее — убрать так: git rm --cached <файл> (или папку целиком через -r), добавить в .gitignore, сделать новый коммит с удалением.

Путаница между git diff и git diff --staged

Очень легко подумать «у меня нет изменений», выполнив git diff, и не заметив, что все изменения уже в индексе. Привычка: если git status показывает блок Changes to be committed:, то git diff по этим файлам будет пустым — смотреть их нужно через git diff --staged.

git commit -am не захватывает новые файлы

Флаг -a работает только с отслеживаемыми файлами. Если Вы создали новый файл и выполнили git commit -am "...", файл в коммит не попадёт, и git status по-прежнему покажет его как untracked. Для новых файлов нужен явный git add.

Попытка «отменить» через reset --hard на общих ветках

git reset --hard переписывает историю ветки. Если эту ветку уже скачали другие, их локальные копии разойдутся с сервером, и следующие git pull вызовут конфликты. Для общих веток — только git revert.

git restore <файл> «вместо» git restore --staged

Две команды звучат почти одинаково, но делают совершенно разное:

  • git restore file — уничтожает правки в файле;
  • git restore --staged file — только убирает из индекса, правки в файле остаются.

Если файл добавлен в индекс и Вы хотите «просто убрать его из коммита» — нужен --staged. Без него Вы потеряете правки.

git commit --amend после push

--amend переписывает коммит и меняет его хеш. Если коммит уже на сервере, следующий git push потребует force-пуша и создаст проблемы для всех, кто этот коммит скачал. Правило: --amend только для локальных коммитов, ещё не отправленных.

Кириллица в сообщениях коммита

Современный Git корректно работает с кириллицей в сообщениях. Но если Вы работаете в команде с иностранцами или на международном проекте — пишите сообщения на английском. Это не правило Git, а правило хорошего тона в команде.

11. Итоги главы

Что нужно вынести из главы 3:

  • git status показывает состояние в нескольких блоках: Changes to be committed (в индексе), Changes not staged (изменено, но не в индексе), Untracked files (новые).
  • git status -s — короткий формат двумя колонками.
  • git diff — рабочая папка ↔ индекс. git diff --staged — индекс ↔ последний коммит. git diff HEAD — рабочая папка ↔ последний коммит.
  • В diff: + — добавленная строка, - — удалённая, пробел в начале — контекст.
  • git add бывает разный: файл, папка, ., -A, -u, -p. git add . — опасен без .gitignore.
  • git commit -m — обычный. git commit -am — с авто-добавлением отслеживаемых (новые файлы не захватит). --amend — переписать последний (только локальный).
  • .gitignore — список шаблонов для игнорирования. Файл должен быть в корне репозитория и закоммичен. Уже отслеживаемый файл убирается через git rm --cached.
  • Отмена: git restore (файл), git restore --staged (индекс), git commit --amend (последний коммит), git reset --soft/--hard HEAD~1 (откат), git revert <хеш> (безопасная отмена опубликованного).
  • git reset --hard — необратимо. Использовать только когда полностью уверены.
  • Для общих веток — revert, для локальных — reset.
